# แผนเชื่อมต่อ Facebook Page / LINE OA / SMS / Telegram

สถานะตอนนี้: **Facebook Page ใช้งานจริงแล้ว** (เชื่อมผ่านปุ่ม, รับ/ส่งข้อความและใบเสนอผ่าน Edge Functions ดู "ฝั่งเซิร์ฟเวอร์ Facebook" ด้านล่าง) · **Telegram ส่งจริงแล้ว** ผ่าน Edge Function `telegram-send` (ตั้ง secret `TELEGRAM_BOT_TOKEN` และ `TELEGRAM_CHAT_ID` ที่ Supabase แล้ว; ส่งได้เฉพาะพนักงานที่ล็อกอิน จำกัด 20 ข้อความ/นาที และ 300 ข้อความ/ชั่วโมง; ไม่เก็บข้อความใน log) · **LINE OA ยังจำลอง** ข้อความบันทึกลงคิว (`db.outbox`) ยังไม่ส่งจริง · **SMS** ส่งจริงผ่าน Edge Function `sms-send` → SMS Gateway บนโทรศัพท์ (API `POST /v1/sms`) เมื่อตั้งค่า secrets ครบ และต้องมีรีเลย์/Tunnel ที่เข้าถึง LAN ได้ (ดูหัวข้อ SMS ด้านล่าง)
ตั้งค่าได้ที่หน้า **จัดการ → การเชื่อมต่อ & แจ้งเตือน** (`/manage/integrations`)

ลำดับที่จะทำจริง: **Telegram → LINE OA → SMS → Facebook Page**

**ศูนย์รวมแชท** (หน้า /chat หลังบ้าน) รวมแชทจาก LINE OA และ Facebook Page ไว้ตอบที่เดียว ลูกค้าไม่ต้องเข้าเว็บ ตอนนี้จำลอง (ปุ่ม "จำลองข้อความเข้า") ต่อจริงด้วย webhook → ตาราง `conversations` / `messages` และตอบผ่าน LINE Reply/Push API, Facebook Send API · การ์ดใบเสนอส่งเป็น LINE Flex / Facebook button template ปุ่ม "ยืนยันสั่ง / ขอแก้" เป็น postback กลับมาที่ webhook แล้วสร้างออร์เดอร์อัตโนมัติ · คนที่ทักครั้งแรกขึ้นชื่อโปรไฟล์ + "ยังไม่ผูก" พนักงานผูกกับลูกค้า (จำ userId/PSID)

## ใช้ทำอะไร

| ใช้ทำ | ช่องทาง |
|---|---|
| แจ้งลูกค้าอัตโนมัติ (สรุปออร์เดอร์, แจ้งยอด, ยืนยันชำระ, เตือนนัด, ส่งมอบ, ยกเลิก) | LINE OA → Facebook → SMS |
| เตือนวันเกิด / คะแนนใกล้หมดอายุ / โปร (เฉพาะลูกค้าที่รับข่าว) | LINE OA, Facebook |
| แจ้งทีมภายใน (ออร์เดอร์ใหม่, ชำระแล้ว, งานใกล้เวลา, ยกเลิก) | Telegram |
| รับแชทเข้าระบบ (ระยะถัดไป) | LINE OA, Facebook |

## สถาปัตยกรรม (เมื่อต่อ Supabase)

```
หน้าเว็บ (Vue) ──เขียน──▶ ตาราง outbox (Supabase)
                               │  Database Webhook / pg_cron
                               ▼
                     Edge Function: dispatch ──▶ Telegram / LINE / SMS / Facebook
                               │ อัปเดต status = sent | failed, attempts, error
LINE / Facebook ──webhook──▶ Edge Function: webhook-line / webhook-facebook
                               ▼
                     ตาราง conversations / messages (รับแชท) + ผูก customers
pg_cron (ทุก 15 นาที) ──▶ Edge Function: scheduled (เตือนนัด 24 ชม., งานใกล้เวลา 2 ชม., วันเกิด, คะแนนใกล้หมด)
```

- **token ทั้งหมดอยู่ใน Supabase secrets เท่านั้น** หน้าเว็บไม่เคยเห็น token
- หน้าเว็บเขียนแค่แถว `outbox` (ผ่าน RLS) หรือเรียก Edge Function ที่ตรวจสิทธิ์แล้ว
- ส่งไม่สำเร็จจะลองใหม่ 3 ครั้ง (1, 5, 15 นาที) แล้วจึงตั้งเป็น failed และแจ้งทีมผ่าน Telegram

### ตาราง (ร่าง)
- `notify_rules (event pk, channels text[], template text, enabled bool)`
- `outbox (id, created_at, event, channel, to_address, text, order_id, customer_id, status, attempts, error, sent_at)`
- `notify_sent (key pk, created_at)` กันส่งซ้ำของเหตุการณ์ตามเวลา
- `customers` เพิ่ม `line_user_id`, `fb_psid`, `fb_last_inbound_at`, `promo_opt_in`
- `conversations (id, channel, external_id, customer_id, last_message_at)` และ `messages (id, conversation_id, direction, text, attachments, created_at)`

## รายละเอียดแต่ละช่องทาง

### 1. Telegram (แจ้งทีมภายใน)
- **เตรียม:** สร้างบอทกับ @BotFather → ได้ `BOT_TOKEN` · เพิ่มบอทเข้ากลุ่มทีม → หา `chat_id` (ผ่าน getUpdates)
- **API:** `POST https://api.telegram.org/bot<TOKEN>/sendMessage { chat_id, text }`
- **ค่าใช้จ่าย:** ฟรี
- **ข้อจำกัด:** ส่งเข้ากลุ่มได้ประมาณ 20 ข้อความ/นาที

### 2. LINE OA (ลูกค้า)
- **เตรียม:** LINE Official Account + เปิด Messaging API ใน LINE Developers → `CHANNEL_ACCESS_TOKEN`, `CHANNEL_SECRET` · ตั้ง Webhook URL ไปที่ Edge Function
- **ผูกลูกค้า:** ต้องได้ `userId` ของลูกค้า (LINE ID ที่ลูกค้าบอกใช้ส่งไม่ได้) ได้จาก
  - event `follow` / ข้อความแรกที่ลูกค้าทัก → แสดงในหน้าแชทให้พนักงานกด "ผูกกับลูกค้า"
  - หรือลิงก์ LINE Login ในหน้าลูกค้า/ใบสรุปออร์เดอร์ (ลูกค้ากดแล้วผูกอัตโนมัติ)
- **API:** push message `POST /v2/bot/message/push` (ตอบกลับภายในแชทใช้ reply ฟรี)
- **ค่าใช้จ่าย:** push นับโควตาตามแพ็กเกจ OA เกินโควตาคิดเงิน
- **รับแชท:** webhook `message` → ตาราง messages
- **ปุ่ม "เชื่อม LINE OA" (วาง token ครั้งเดียว):** หน้าเว็บส่ง token + secret ไป Edge Function `connect-line` (เก็บใน DB ฝั่งเซิร์ฟเวอร์ หน้าเว็บเก็บแค่ 4 ตัวท้าย) → `GET /v2/bot/info` ตรวจ token + ได้ชื่อบอท → `PUT /v2/bot/channel/webhook/endpoint` ตั้ง Webhook URL → `POST /v2/bot/channel/webhook/test` ทดสอบ · LINE ไม่มีปุ่มคลิกเดียวสำหรับร้านทั่วไป (ต้องเป็นพาร์ทเนอร์ LINE)

### 3. SMS (ลูกค้า สำรอง)
- **เตรียม:** ติดตั้งแอป SMS Gateway บนโทรศัพท์ Android 14+ ที่มีซิม → ตั้งพอร์ต (ค่าเริ่มต้น 8443) → สร้าง API key สิทธิ์ **ส่งและลบ** → คัดลอก certificate pin (`sha256//…`) จากหน้าหลักของแอป
- **ค่าใช้จ่าย:** คิดต่อข้อความ ภาษาไทย 70 ตัวอักษร/ข้อความ (ยาวกว่านั้นนับหลายข้อความ) จึงควรใช้ข้อความสั้น
- **ใช้เมื่อ:** ลูกค้าไม่ได้ผูก LINE/Facebook และมีเบอร์โทร

### 4. Facebook Page (ลูกค้า)
- **เตรียม:** Meta Developer App + เชื่อม Page → Page Access Token · ขอสิทธิ์ `pages_messaging` (ต้องผ่าน App Review) · ตั้ง Webhook
- **ผูกลูกค้า:** ได้ `PSID` เมื่อลูกค้าทักเพจ → ผูกในหน้าแชท
- **ข้อจำกัด:** ส่งได้ภายใน 24 ชม. หลังลูกค้าทักล่าสุด นอกช่วงต้องใช้ message tag ที่อนุญาต (เช่น `POST_PURCHASE_UPDATE` สำหรับแจ้งสถานะออร์เดอร์) ห้ามใช้ส่งโปร
- **API:** Send API `POST /me/messages`
- **ปุ่ม "เชื่อม Facebook" (คลิกเดียว):** Facebook Login for Business ขอสิทธิ์ `pages_show_list`, `pages_messaging`, `pages_manage_metadata` → Edge Function แลก long-lived user token → `GET /me/accounts` ให้เลือกเพจ → เก็บ Page Access Token ฝั่งเซิร์ฟเวอร์ → `POST /{page-id}/subscribed_apps` (fields=messages,messaging_postbacks) สมัครรับ webhook

## เหตุการณ์ → ช่องทาง (ค่าเริ่มต้น)

| เหตุการณ์ | ผู้รับ | ช่องทาง | เกิดเมื่อ |
|---|---|---|---|
| สร้างออร์เดอร์ (สรุป) | ลูกค้า | LINE, Facebook, SMS | สร้างออร์เดอร์ / ร่าง → ส่งไปรอชำระ |
| แจ้งยอดชำระ | ลูกค้า | LINE, Facebook, SMS | กดแจ้งยอดชำระ |
| ยืนยันชำระแล้ว | ลูกค้า | LINE, Facebook, SMS | แอดมินยืนยันยอด |
| เตือนก่อนนัดรับ | ลูกค้า | LINE, Facebook, SMS | ตามเวลา: ก่อนนัด 24 ชม. |
| ส่งมอบแล้ว | ลูกค้า | LINE, Facebook | เปลี่ยนสถานะเป็นส่งมอบ |
| ยกเลิกออร์เดอร์ | ลูกค้า | LINE, Facebook, SMS | ยกเลิกออร์เดอร์ |
| อวยพรวันเกิด | ลูกค้า (รับข่าว) | LINE, Facebook | ตามเวลา: ภายในวันเตือนวันเกิดที่ตั้งไว้ |
| คะแนนใกล้หมดอายุ | ลูกค้า (รับข่าว) | LINE, Facebook | ตามเวลา: ภายใน 30 วัน |
| ออร์เดอร์ใหม่ / ชำระแล้ว / ยกเลิก | ทีม | Telegram | พร้อมเหตุการณ์ลูกค้า |
| งานใกล้เวลาต้องเสร็จ | ทีม | Telegram | ตามเวลา: ก่อนเวลาต้องเสร็จ 2 ชม. |
| บรอดแคสต์โปร (ระยะถัดไป) | ลูกค้า (รับข่าว) | LINE (broadcast/narrowcast) | กดส่งจากหน้าจัดการ |

**ลำดับเลือกช่องทางถึงลูกค้า:** ช่องทางแรกที่ (อนุญาตในกฎ + เปิดใช้ + ลูกค้ามีข้อมูล) ตามลำดับ LINE → Facebook → SMS (ข้อความทาง LINE/Facebook ขึ้นในศูนย์รวมแชทด้วย)
ถ้าไม่มีเลย บันทึกในคิวว่า "ไม่มีช่องทาง"

**ตัวแปรในข้อความ:** `{ชื่อลูกค้า} {เลขออร์เดอร์} {ยอดรวม} {คงค้าง} {ยอดที่แจ้ง} {วันนัด} {เวลานัด} {ส่งมอบ} {ชื่อวันเกิด} {คะแนน}`

## ความยินยอม (PDPA)
- ข้อความเกี่ยวกับออร์เดอร์ (สรุป แจ้งยอด เตือนนัด) ส่งได้ตามสัญญาซื้อขาย
- ข่าวโปร/อวยพรวันเกิด/คะแนนใกล้หมด ส่งเฉพาะลูกค้าที่เปิด "รับข่าวโปร" และต้องมีวิธีขอยกเลิก (พิมพ์ "ยกเลิกรับข่าว" ใน LINE → webhook ปิดให้อัตโนมัติ)

## รับแชทเข้าระบบ (ระยะถัดไป)
- หน้า "แชท" รวม LINE + Facebook เรียงตามล่าสุด มีป้ายช่องทาง
- ผูกแชทกับลูกค้า (ค้นชื่อ/เบอร์) → เก็บ `line_user_id` / `fb_psid`
- ตอบกลับจากหลังบ้าน (LINE reply/push, Facebook ภายใน 24 ชม.)
- ปุ่ม "สร้างออร์เดอร์จากแชท" เติมลูกค้าให้อัตโนมัติ
- **แชทอัจฉริยะ (ทำแล้วในหน้าเว็บ `src/lib/chatParse.js`):** จับเบอร์ / วันที่ / เวลาในข้อความลูกค้าเป็นชิป กดเพื่อกรอกลงร่างออร์เดอร์ · ปุ่มถาม (ขอเบอร์ / วันเวลารับ / ที่อยู่ / ข้อความบนเค้ก / ชื่อ) คำตอบถัดไปของลูกค้าผูกกับคำถามและกรอกลงร่างอัตโนมัติ · ตอบกลับอ้างข้อความ · ข้อความสำเร็จรูป

## Checklist เปิดใช้งานจริง
1. ต่อ Supabase (ตาราง + RLS + Edge Functions `dispatch`, `scheduled`) และย้าย `notify()` จาก `src/data/store.js` ไปเขียนแถว outbox
2. **Telegram:** สร้างบอท → ใส่ `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` ใน secrets → ทดสอบส่ง
3. **LINE OA:** สร้าง Messaging API channel → ใส่ `LINE_CHANNEL_ACCESS_TOKEN`, `LINE_CHANNEL_SECRET` → ตั้ง webhook → ทำการผูก userId
4. **SMS:** ตั้งแอป SMS Gateway บนโทรศัพท์ → ตั้ง `SMS_GATEWAY_URL` (ลิงก์รีเลย์/เกตเวย์) และ `SMS_API_KEY` (สิทธิ์ส่งและลบ) → ทดสอบ
5. **Facebook:** สร้าง Meta App (Facebook Login for Business + Config ID) → ขอ App Review `pages_messaging`, `pages_show_list`, `pages_manage_metadata` → ตั้ง secrets `FB_APP_ID`, `FB_APP_SECRET`, `FB_CONFIG_ID`, `FB_VERIFY_TOKEN` (ดูหัวข้อ "ฝั่งเซิร์ฟเวอร์ Facebook") → ตั้ง Webhook URL → เชื่อมเพจจากหน้า /admin/settings/integrations (ไม่ต้องใส่ Page token เอง)
6. เปิด pg_cron สำหรับเหตุการณ์ตามเวลา
7. ทำหน้าแชท (ระยะถัดไป)

## รอบ E: Telegram / SMS (จำลอง) · แนะนำสินค้า · บอทตอบแชท

### Telegram / SMS (หน้า `/admin/settings/integrations`)
- Telegram: วาง bot token (จาก @BotFather) + chat id → "เชื่อม" · ตรวจรูปแบบเท่านั้น (ยังไม่ยิง API จริง) · เก็บเฉพาะ **4 ตัวท้าย** ของ token · ปุ่ม "ส่งข้อความทดสอบ" ลงคิวข้อความ (สถานะ simulated)
- SMS: ช่อง URL ผู้ให้บริการ (**https เท่านั้น · ชื่อโดเมนเท่านั้น ไม่รับ IP/localhost/ภายใน** กัน SSRF ตอนเซิร์ฟเวอร์เรียกจริง · ห้าม user:pass) + ชื่อผู้ส่ง (A-Z a-z 0-9 . _ - 3–11 ตัว) + API key (เก็บ 4 ตัวท้าย) · ปุ่มทดสอบใส่เบอร์ → ลงคิว
- **ส่งจริงผ่าน Edge Function `sms-send`** (`supabase/functions/sms-send/index.ts`) ตาม SMS Gateway API v1: ตรวจสิทธิ์พนักงาน (punpang_staff active) → ตรวจเบอร์ (0 หรือ 66/+66 + 8–9 หลัก แล้วส่งเป็น 0…) → ตรวจความยาวไม่เกิน 350 ตัวอักษร (5 ฉบับ) → `POST {ราก}/v1/sms` พร้อม `Authorization: Bearer <key>` และ `Idempotency-Key` จากฝั่งเรียก (`row.idem` ทำให้ลองซ้ำไม่ส่งซ้ำ) · 202 = งานใหม่, 200 = คืนงานเดิมของคีย์นี้ · ตอบ `{ok, id, status, created}`
- **actions ของ `sms-send`:** `status` (secret ครบหรือยัง) · `gateway` (`GET /v1/status`) · `send` (ค่าเริ่มต้น; รับ `sim` 1/2 ได้) · `lookup` (`GET /v1/sms/{id}`) · `messages` (`GET /v1/messages?direction&limit&before`, แบ่งหน้าด้วย `next_before`)
- **ไม่มีฟอร์มกรอก URL/คีย์ SMS ในหน้าการเชื่อมต่อแล้ว:** ค่าอยู่ที่ Supabase secrets เท่านั้น สถานะ SMS ตั้งอัตโนมัติเมื่อ `status` ได้ `configured` (`src/lib/staffAuth.js`)
- **หน้าจัดการ** `/admin/settings/sms`: สถานะ/นับงาน, ส่งทดสอบ, ตรวจสถานะงาน, รายการข้อความจากแอป
- **ข้อจำกัดของ API:** ข้อความหลายฉบับ ถ้าฉบับใดไม่สำเร็จ แอปจะลองส่งทั้งข้อความใหม่ (ฉบับแรกอาจซ้ำ) · การลองส่งรวม 4 ครั้ง แล้วสถานะเป็น `FAILED` · `sms.sent` / `SENT` หมายถึง radio รับงานแล้ว ยังไม่รับรองว่าถึงผู้รับ · โควตาต่อวันไม่นับคำขอที่ใช้คีย์ซ้ำ · key ผูกกับ IP ได้ในแอป · `GET /v1/*` ใช้ได้กับ key สิทธิ์อ่านอย่างเดียว ส่วนการส่งต้องใช้สิทธิ์ส่งและลบ
- **ยังไม่ได้ทำ:** webhook ขาเข้า (`sms.received`/`sms.delivered`/`sms.failed`), การลบข้อความ, การตั้งค่าการเก็บข้อความ (`/v1/settings/retention`)
- **ตั้งค่าฝั่งเซิร์ฟเวอร์ (secret):** `supabase secrets set SMS_GATEWAY_URL=<ลิงก์ http/https ของเกตเวย์หรือรีเลย์> SMS_API_KEY=<key สิทธิ์ส่งและลบ>` ไม่มี secret ครบ = ฟังก์ชันตอบ "ยังไม่ได้ตั้งค่า" · ไม่ต้องตั้ง `SMS_SENDER` แล้ว (ไม่ใช้กับ API นี้)
- **ข้อจำกัดสำคัญ:** เกตเวย์รับคำขอเฉพาะจาก IP ใน LAN และใช้ใบรับรอง self-signed ที่ตรวจด้วย pin ระบบบนคลาวด์ (Supabase) เข้าถึง LAN ไม่ได้โดยตรง ต้องมีรีเลย์ในวง LAN หรือ Tunnel/VPN ก่อนการส่งจริงจะผ่าน
- **ข้อจำกัดของ API:** ข้อความ ≤160 ตัวอักษร · เกินโควตาต่อวันได้ 429 `daily_limit_reached` · ส่งซ้ำด้วย key เดิมไม่สร้างงานซ้ำ
- **ยังไม่มี:** จำกัดอัตราการส่งต่อผู้ใช้ และบันทึก log ลงตาราง (ทำได้เมื่อจำเป็น)
- โค้ด: `src/lib/integrationCheck.js` · `connectTelegram/connectSms/sendIntegrationTest` ใน store

#### บอท AI (Claude API · ช่อง Facebook เท่านั้น)

- **คีย์:** ตั้ง secret `ANTHROPIC_API_KEY` ของ Supabase ผ่านฟอร์มที่ปลอดภัยเท่านั้น (ห้ามวางในแชท/โค้ด) · ไม่มีคีย์ = บอท AI ไม่ทำงาน ส่งต่อพนักงานตามปกติ
- **ข้อมูลที่ส่งออก:** เฉพาะข้อความปัจจุบันของลูกค้า + ชื่อร้าน เวลาทำการ คำถามที่พบบ่อย และสินค้าพร้อมขาย/ราคา (`punpang_items` ที่แสดงหน้าร้าน) + ชื่อประเภท/เนื้อเค้กสั่งทำ (สำเนาสาธารณะ `shop_public` ไม่มีสูตรหรือต้นทุน)
- **งดส่งข้อมูลส่วนตัว:** ไม่ส่งประวัติแชท ข้อความพนักงาน หรือชื่อลูกค้า · ถ้าข้อความมีเบอร์/อีเมล/เลขออร์เดอร์/เลขยาว หรือมีชื่อลูกค้า → **ไม่เรียก AI** และส่งต่อพนักงาน · ไม่ส่งข้อมูลออร์เดอร์ ยอดเงิน หรือแต้ม
- **ราคา:** ตอบได้เฉพาะราคาสินค้าพร้อมขายในรายการ · ราคาเค้กสั่งทำไม่อยู่ในข้อมูลนี้ → ส่งต่อพนักงาน
- **เพดาน:** `dailyLimit` ครั้งต่อวัน (เวลาไทย) นับอะตอมิกด้วย `punpang_ai_take` (migration `20261111100000`) · ควรตั้งงบใช้จ่ายที่ผู้ให้บริการ Anthropic ด้วย
- **บันทึก:** ทุกการเรียกลง `punpang_records` collection `aiLog` (สถานะ ok/handoff/error/limit · ข้อความลูกค้าตัด 200 ตัวอักษร · ไม่มีคีย์)
- **ยังไม่มี:** ราคาเค้กสั่งทำให้ AI (ส่งต่อพนักงาน) · ผู้ให้บริการอื่นนอกจาก Anthropic · สถิติรายวันบนหน้าจอ
- โค้ด: `supabase/functions/_shared/ai.ts` (อะแดปเตอร์) · `supabase/functions/fb-webhook/bot.ts` (`tryAi`, `aiSystemPrompt`, `scrubPII`) · ทดสอบ `node bot.test.mts` (mock fetch/rpc)
- **ก่อนเปิดจริง:** deploy `fb-webhook` + ตั้ง secret + apply migration (ต้องอนุมัติทุกครั้ง) → ทดสอบบัญชี Messenger ทดสอบในโหมดร่างก่อน → ค่อยพิจารณาโหมดส่งเอง

## ฝั่งเซิร์ฟเวอร์ Facebook (Edge Functions)
- **โค้ดอยู่ในรีโป:** `supabase/functions/fb-connect`, `fb-send`, `fb-webhook` (คัดลอกจากที่ deploy บนโปรเจกต์ `punpang` แล้ว) · ตาราง `punpang_fb_pages` (token เพจ), `punpang_fb_oauth` (state ชั่วคราว), `punpang_chats`, `punpang_quotes` อยู่ใน `supabase/migrations/20261110130000_punpang_facebook_tables.sql` (`if not exists` รันซ้ำได้)
- **ความปลอดภัย:** `punpang_fb_pages` และ `punpang_fb_oauth` เปิด RLS แบบไม่มี policy โดยตั้งใจ → เข้าถึงได้เฉพาะ service role ใน Edge Functions เท่านั้น
- **Secrets ที่ต้องตั้ง** (`supabase secrets set`): `FB_APP_ID`, `FB_APP_SECRET`, `FB_CONFIG_ID`, `FB_VERIFY_TOKEN` (≥8 ตัวอักษร, ใช้ตอน verify webhook), ตัวเลือก `FB_GRAPH_VERSION` (ค่าเริ่มต้น v24.0), `FB_APP_URL` (ค่าเริ่มต้น `https://cake-order-admin.pages.dev` ใช้เป็นที่กลับหลัง OAuth · ตั้ง secret ให้ตรงกับโดเมนที่ใช้จริงเสมอ)
- **ตรวจสถานะ:** เรียก `fb-connect` action `status` → `configured: true/false` และเพจที่เชื่อม
- **Webhook ของ Meta:** Callback URL = `<SUPABASE_URL>/functions/v1/fb-webhook` · Verify token = `FB_VERIFY_TOKEN` · subscribed fields `messages`, `messaging_postbacks` (แอปสมัครให้เองตอนเชื่อมเพจ)
- **บอทฝั่งเซิร์ฟเวอร์:** ตอบ 200 ให้ Meta ก่อน แล้วบอททำงานต่อเบื้องหลัง (`EdgeRuntime.waitUntil`) · นอกเวลาทำการตอบครั้งเดียวต่อช่วงปิด (ไม่ตอบซ้ำทุกข้อความระหว่างที่ร้านปิด) · ชุดทดสอบ `supabase/functions/fb-webhook/bot.test.mts` รันด้วย `node bot.test.mts` ในโฟลเดอร์นั้น
- **การตั้ง verify JWT ของแต่ละฟังก์ชัน (ค่าที่ deploy อยู่):** `fb-send` = เปิด (`verify_jwt` true) · `fb-connect` = ปิด และตรวจ JWT พนักงานในฟังก์ชันเอง · `fb-webhook` = ปิด (ตรวจลายเซ็น Meta แทน) · อย่า deploy ทับโดยไม่ตรวจว่าโค้ดในรีโปตรงกับที่ใช้งานอยู่ และรักษาค่านี้ตามเดิม

- **บอทตอบ Facebook ฝั่งเซิร์ฟเวอร์ (Phase 1):** `supabase/functions/fb-webhook/bot.ts` ทำงานหลังบันทึกข้อความตัวอักษรใหม่ของลูกค้าแล้ว ไม่ต้องมีพนักงานเปิดแอป · เปิดได้เมื่อ `punpang_kv` (collection `config`, id `bot`) มี `enabled: true` และ `channels.facebook: true` (ค่าเริ่มต้นปิด)
  - **ตอบเอง** (เฉพาะประเภทที่ `sourceModes` ตั้งเป็น `auto`): เวลาเปิด (ถ้ามีวันปิดพิเศษ ส่งต่อแทน) · นอกเวลาทำการ · FAQ ที่ตรงชัด (อ่านจาก collection `storefront` id `storefront` ถ้ามี) · กฎคีย์เวิร์ด

  - ข้ามเมื่อ: แชทปิดบอท (`botOff`) · ข้อความเก่ากว่า 5 นาที · พนักงานตอบไปแล้วหลังข้อความนั้น · ตอบข้อความ mid นี้ไปแล้ว (กันซ้ำเมื่อ Meta ส่งซ้ำ) · รูป/ไฟล์ล้วน
  - ส่งผ่าน Graph `me/messages` (`messaging_type: RESPONSE`) บันทึกลงแชทด้วย `by: 'บอท'` และ `delivery` ตามผลส่งจริง · ข้อผิดพลาดของบอทถูกจับไว้ ไม่ทำให้ Meta ส่งซ้ำ
  - **ยังไม่ทำใน Phase 1:** ราคา/แนะนำสินค้า · ขอเบอร์/วันนัด · เลขออร์เดอร์ที่ยืนยันตัวตนได้ · การเรียนรู้คำตอบจากพนักงาน · ข้อความแจ้งร้านปิดครั้งแรกของวัน (closedNotice) · หน่วงเวลา `delaySec` · สถิติบอท (ยังนับในเบราว์เซอร์เท่านั้น)
  - **เบราว์เซอร์ไม่ตอบ Facebook แล้ว** (`SERVER_BOT_CHANNELS` ใน `src/data/store.js`) → หลัง deploy บอทตอบ Facebook เฉพาะที่เซิร์ฟเวอร์ · LINE ยังตอบในเบราว์เซอร์
  - **ต้องทดสอบจากบัญชี Messenger ทดสอบก่อนเปิดใช้จริง** และ deploy `fb-webhook` เมื่อได้รับอนุมัติเท่านั้น (ทับโค้ดที่ใช้งานอยู่)
- **แชทปกติ:** ข้อความที่เป็นรูป/ไฟล์ล้วนไม่ผ่านบอท
- **ไฟล์แนบจากลูกค้า**: `fb-webhook` เก็บสำเนาใน bucket private `punpang-chat` (จำกัด 8MB/ไฟล์ ชนิดตาม allowlist) แล้วแอปขอ signed URL ตอนแสดง · ไม่มีการลบอัตโนมัติ (พื้นที่เก็บโตตามจำนวนรูป) · รับและแสดงเท่านั้น ยังไม่ส่งรูปตอบลูกค้า
- **กันข้อความหาย**: เขียนแชทแบบ compare-and-swap ด้วย `updated_at` ชนกัน → รวมข้อความตาม id · หน้าแชทรีเฟรชทุก ~10 วิ (หน้าอื่น 45 วิ)
- **ผูกลูกค้า**: ระบบแนะนำจากเบอร์ในแชท/ชื่อที่คล้าย พนักงานกดผูกเอง ไม่ผูกอัตโนมัติ
- **แจ้งลูกค้าทาง Facebook**: ข้อความอัตโนมัติ การ์ดสรุปออร์เดอร์ และใบเสนอ ส่งถึง Messenger จริง (การ์ดออร์เดอร์เป็นข้อความสรุป · **ใบเสนอมีปุ่ม [ยืนยันสั่ง]/[ขอแก้ไข]** แบบ postback) · สถานะในรายการส่งออกตามผลส่งจริง · ส่งไม่ได้ (เกิน 24 ชม. / ไม่มีแชทที่ผูกไว้ / Facebook ปฏิเสธ) → ขึ้นกระดิ่ง "แจ้งลูกค้าไม่สำเร็จ" ให้พนักงานตามเอง

### ปุ่มในใบเสนอ (postback)
- `fb-send` ส่งใบเสนอเป็น button template (ข้อความ ≤640 ตัว) ปุ่ม payload `q:ok:<quoteId>` / `q:rev:<quoteId>` · เซิร์ฟเวอร์ตรวจว่าใบเสนอเป็นของแชทนี้และสถานะ `pending` ก่อนสร้างปุ่ม
- `fb-webhook` รับ postback: ตรวจเจ้าของแชท · เปลี่ยนสถานะครั้งเดียวจาก `pending` (compare-and-set) · กดซ้ำ/Meta ส่งซ้ำไม่ซ้ำ (mid) · ยืนยัน → `customer_ok` (ใบเสนอเลยเวลานัดแล้ว → ไม่รับ) · ขอแก้ → `revise` และบอกลูกค้าให้พิมพ์สิ่งที่ต้องการแก้ · ตอบลูกค้าทันที
- สร้างออร์เดอร์: **หน้าแอดมินที่เปิดอยู่** พบใบเสนอ `customer_ok` → จองสิทธิ์ผ่าน RPC `punpang_quote_claim` (ครั้งเดียว) → `processQuoteConfirm` สร้างออร์เดอร์ (แชทยังไม่ผูกลูกค้า → สถานะ `need_phone` ขอเบอร์) · ไม่มีใครเปิดแอป = ออร์เดอร์ยังไม่ถูกสร้างจนกว่าจะเปิด
- ข้อจำกัด: ปุ่มกดได้ภายใน 24 ชม. · แอปที่ยังไม่เผยแพร่ ผู้กดต้องมี Role ในแอป Meta

- ส่งเป็นการ์ด: **ใบเสนอ** (ปุ่ม [ยืนยันสั่ง]/[ขอแก้ไข]) · **สรุปออร์เดอร์** (ไม่มีปุ่ม) · **ลิงก์ออร์เดอร์** (ปุ่มเปิดลิงก์ ต้องเป็น https) · อย่างอื่น (แจ้งสถานะ/ชำระเงิน, ข้อความพนักงาน/บอท) คงเป็นข้อความ

- โค้ด: `orderCardMsg/quoteCardMsg/linkCardMsg` ใน `src/lib/chatCards.js`

## การซิงก์กับเซิร์ฟเวอร์ + สถานะรอ/ผิดพลาด (โหมด Supabase)
- **ไม่มีข้อมูลตัวอย่างแทนข้อมูลจริง**: โหมด Supabase ไม่สร้าง demo · หน้าร้านแสดงโครงรอจนโหลดจากเซิร์ฟเวอร์เสร็จ โหลดไม่ได้ = ข้อความผิดพลาด + ปุ่มลองใหม่ · หลังบ้านโหลดตารางไม่สำเร็จ = ล้างรายการตัวอย่าง + แถบแดง "โหลดข้อมูลจากเซิร์ฟเวอร์ไม่สำเร็จ (…)" + ปุ่มลองโหลดใหม่ (`staffState.loadFailed`)
- **หน้าร้านรีเฟรชเอง**: กลับมาที่แท็บ/ทุก 60 วินาที (`loadPublicNow` ใน `staffAuth.js`) ให้สต็อก/ราคาตรงเซิร์ฟเวอร์
- **แถบสถานะบันทึก** (`SyncBar.vue`, `src/lib/syncStatus.js`): รอบันทึก/กำลังบันทึก/ล้มเหลว · ล้มเหลว = ลองซ้ำเอง 5→15→60 วินาที (`RETRY_MS` ใน `tableSync.js`/`configSync.js`) + ปุ่ม "ลองใหม่ตอนนี้" · ปิดแท็บขณะมีข้อมูลค้างเขียน = เบราว์เซอร์เตือน · ออฟไลน์ = แถบเหลือง
- **รอเซิร์ฟเวอร์ก่อนแจ้งสำเร็จ**: `waitSaved()/toastSaved()` ใช้กับสร้างออร์เดอร์ (ไม่สร้างซ้ำถ้ากดบันทึกอีกครั้ง) · เปลี่ยนสถานะ · แจ้ง/ยืนยัน/รับชำระ · ขาย POS (แสดงใบเสร็จได้ แต่แจ้งสีแดงถ้ายังไม่ขึ้นเซิร์ฟเวอร์) · ก่อนขาย POS ดึงสต็อก/กะล่าสุด (`refreshLabels`)
- **รีเฟรชเพิ่ม**: สินค้า กะ POS และตั้งค่า (`configSync.refresh`) ดึงใหม่ทุก 45 วินาที ข้ามถ้ามีแก้ค้างในเครื่อง
- **ลิงก์ออร์เดอร์**: เครือข่ายล่ม/5xx = "เชื่อมต่อไม่ได้" + ลองใหม่ (ไม่ใช่ "ลิงก์หมดอายุ") · ปุ่มฝั่งลูกค้าที่รอเซิร์ฟเวอร์มีสถานะกำลังดำเนินการกันกดซ้ำ
- **ไม่ได้ทำรอบนี้**: แลกแต้ม/สุ่มกาชา/คูปองของลูกค้า และตัดสต็อก POS แบบ atomic ฝั่งเซิร์ฟเวอร์ · compare-and-swap ของออร์เดอร์/ลูกค้า (ยังเขียนทั้งก้อนแบบ last-write-wins)

## Realtime + ย่อรูปก่อนอัปโหลด
- Realtime: ตาราง `punpang_orders/customers/items/shifts/chats/quotes/kv/records` อยู่ใน publication `supabase_realtime` · เมื่อมี event แอปหน่วง ~0.3–0.4 วิ แล้วเรียก `refresh()` เดิมของตารางนั้น (ข้ามเมื่อมีแก้ค้างในเครื่อง · ไม่ apply payload ตรง) — `src/lib/realtimeSync.js`
- พนักงาน: channel `staff-sync` (ตามสิทธิ์ที่มี) · เชื่อมอยู่ = poll ทั้งหมดแค่ทุก 5 นาที, หลุด = กลับทุก 45 วินาที + แถบเตือน "ข้อมูลสดขาดการเชื่อมต่อ" (SyncBar) · reconnect/กลับมาออนไลน์/กลับมาที่แท็บ = ดึงทั้งหมดทันที
- ผู้เยี่ยมชม: channel `public-sync` (kv shop_public/storefront/legal, items, records reviews/shortLinks) → โหลดข้อมูลสาธารณะใหม่ · poll 60 วินาทีเป็นสำรอง · หน้าออร์เดอร์/ลิงก์ลูกค้าไม่ใช้ (ใช้ token ไม่ใช่ JWT)
- รูป: `src/lib/imageResize.js` ย่อด้านยาว ≤1000px และ ≤2 MB (JPEG พื้นขาว) ก่อนอัปโหลดทุกจุด (ImageUploader, สลิปแอดมิน/ลูกค้า, รูปอ้างอิงออร์เดอร์) · `storage.js` ปฏิเสธไฟล์ >2 MB

## การ์ด Messenger (ปรับหน้าตา)
- การ์ดออร์เดอร์/ใบเสนอ/ลิงก์: หัวข้อสั้น (`ออร์เดอร์ <รหัส>`), บรรทัดรอง `ยอดรวม … · ค้างชำระ …` (ไม่มี "บาท" ซ้ำกับ ฿), รูปบนการ์ด = รูปสินค้าชิ้นแรก (https) → ไม่มีใช้รูปหน้าร้าน (storefront.heroImage) → ไม่มีก็ไม่ใส่รูป (ยังไม่มีช่องโลโก้ร้านในระบบ)
- การ์ดออร์เดอร์มีปุ่ม "ดูออร์เดอร์ / โอนเงิน" (ชำระครบ = "ดูออร์เดอร์") ลิงก์ออร์เดอร์สร้างให้อัตโนมัติตอนส่งการ์ด (ยกเว้นร่าง/POS) · แตะการ์ดก็เปิดลิงก์ · รูป/ลิงก์ที่ไม่ใช่ https ถูกข้าม (fb-send v10)

## ส่ง SMS ซ้ำเมื่อแจ้งทางแชท + ข้อความ "ได้รับชำระ"
- แจ้งลูกค้าทาง Facebook/LINE แล้ว ถ้าลูกค้ามีเบอร์ → ส่ง SMS ซ้ำด้วยเสมอ (เฉพาะ event ที่กฎแจ้งเตือนเปิด SMS ไว้ และเปิดช่อง SMS ในระบบ) · SMS ส่งแม้ Messenger เกิน 24 ชม./ส่งไม่ถึง
- ติ๊ก "ส่ง SMS ด้วย" (ค่าเริ่มต้นติ๊ก) อยู่ข้างติ๊ก "แจ้งลูกค้า" ทุกจุด (สร้างออร์เดอร์, แจ้ง/รับ/ยืนยันชำระ, เปลี่ยนสถานะ, ยกเลิก, คืนเงิน, รูปงาน, คำขอไม่เผยแพร่รูป) · แสดงเมื่อลูกค้ามีเบอร์และผูกแชท · ไม่ติ๊ก "แจ้งลูกค้า" = ไม่ส่งทั้งคู่ · งานอัตโนมัติ (เตือนนัด/เตือนชำระ) ส่ง SMS ซ้ำตามค่าเริ่มต้น
- ข้อความ "ได้รับชำระ": ยอดที่ชำระครั้งนี้ · ยอดรวม · ชำระแล้ว · คงค้าง · นัดส่งมอบ · ลิงก์ดูออร์เดอร์ — Facebook ส่งเป็นข้อความ + การ์ดปุ่ม "ดูออร์เดอร์ / โอนเงิน" (ไม่มีบรรทัดลิงก์ซ้ำ), SMS ได้ข้อความเต็มพร้อมลิงก์ · กฎที่ร้านแก้ข้อความเองไม่ถูกแทนที่ (ใช้ข้อความของร้าน แต่ Facebook ยังได้การ์ด)

## แชทมือถือ: แป้นพิมพ์ + ปุ่มสรุปออร์เดอร์
- หน้าล็อก (แชท) ตามขนาดส่วนที่มองเห็นจริง (`visualViewport` → `--vvh`/`--vvt`, `src/lib/viewportFit.js`) แป้นพิมพ์ iOS จึงไม่บังช่องพิมพ์/ปุ่มส่ง · ระหว่างพิมพ์ซ่อนแถบเมนูล่าง และเลื่อนข้อความล่าสุดให้อยู่เหนือช่องพิมพ์
- ปุ่ม "สรุปออร์เดอร์" ในแถบใต้ช่องพิมพ์ (ลูกค้าที่ผูกแชทและมีออร์เดอร์): 1 ใบ → ส่งการ์ดสรุปเลย · หลายใบ → เลือกก่อน (ส่งด้วย `postOrderCard` — การ์ดมีรูป + ปุ่มดูออร์เดอร์/โอนเงิน)

## ข้อความ "เตรียมสินค้าเสร็จ"
- รับที่ร้าน: ต่อท้ายด้วย "สามารถรับสินค้าได้แล้ว แต่ต้องไม่เกินเวลาร้านปิด HH:mm น." (เวลาปิดร้านจาก ตั้งค่าร้าน → เวลาปิดประจำวัน) · จัดส่ง: ไม่มีประโยคนี้ · ตัวแปรใหม่ `{ข้อความรับสินค้า}` `{เวลาปิดร้าน}` · กฎที่ยังเป็นข้อความเริ่มต้นเก่าจะใช้ข้อความใหม่อัตโนมัติ ส่วนที่ร้านแก้เองไม่แตะ

## ข้อความ "ส่งมอบแล้ว"
- ขอบคุณ + (เมื่อออร์เดอร์มีรูปงานและลูกค้ายังไม่เคยขอไม่เผยแพร่) ขออนุญาตนำภาพสินค้าไปใช้เผยแพร่ หากไม่ยินยอมแจ้งได้เลย (กดดูออร์เดอร์ → "ไม่อนุญาตให้ใช้รูปเผยแพร่" หรือแจ้งในแชท) · Facebook ส่งเป็นการ์ดปุ่ม "ดูออร์เดอร์" · ตัวแปรใหม่ `{ข้อความขอใช้ภาพ}` · กฎที่ร้านแก้เองไม่ถูกแทนที่ · กฎนี้ยังไม่ส่ง SMS (เปิดได้ที่ตั้งค่าแจ้งเตือน)

## ลิงก์ดูออร์เดอร์ทุกข้อความ + เตือนชำระ 9 โมงเช้า
- **ทุกข้อความถึงลูกค้าที่เกี่ยวกับออร์เดอร์** (ไม่รวมการตลาด/วันเกิด/คะแนน/POS/ร่าง) มีลิงก์ดูออร์เดอร์เสมอ:
  - **SMS / LINE**: ข้อความมีลิงก์ (ถ้าเทมเพลตไม่มี `{ลิงก์ออร์เดอร์}` ระบบต่อท้ายเป็นบรรทัด `ดูออร์เดอร์: <ลิงก์>`)
  - **Facebook**: การ์ดปุ่ม "ดูออร์เดอร์" (ข้อความบนการ์ดตัดบรรทัดลิงก์ออก เพราะปุ่มทำหน้าที่แทน)
  - โค้ด: `notify()` / `notifyOrder()` / `orderLinkCardOf()` ใน `src/data/store.js`
- **เตือนชำระ (`payment_reminder`)**: ทำงานครั้งเดียวต่อออร์เดอร์ ตอน `payReminderTime` (ค่าเริ่มต้น 09:00) ของวันถัดไป · เลือกออร์เดอร์ที่วันนัดเป็นพรุ่งนี้ มีงวดที่แจ้งชำระไว้ (`reported`) และยังไม่มีการชำระเลย (ไม่มีงวด `confirmed` และ `paid` = 0) · ไม่ส่งถ้าสถานะเป็นยืนยันโดยไม่ชำระ (`order_confirmed`), ลูกค้าแนบสลิปรอตรวจ, หรือยอดคงค้างเป็น 0
- ข้อความเริ่มต้นของเตือนชำระ: "โปรดชำระเงินก่อน {ชำระก่อน} เพื่อยืนยันการสั่งซื้อ {เลขออร์เดอร์} {วันนัด} {เวลานัด} ... ขอบคุณค่ะ" (ค่าเดิมในฐานข้อมูลจะถูกแทนอัตโนมัติ · ค่าที่ร้านแก้เองไม่ถูกแทน)
