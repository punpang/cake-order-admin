# สถานะความปลอดภัย

ผลตรวจโค้ดทั้งระบบ (ฟังก์ชันเซิร์ฟเวอร์ ฐานข้อมูลจริง ฝั่งแอป หน้าจอ/การตั้งค่า) และสิ่งที่แก้แล้ว · รอบล่าสุด 2026-11-14 อยู่ด้านบน รอบ 2026-11-10 อยู่ถัดลงไป

## รอบแก้ 2026-11-15 (ต่อจากผลตรวจ main `0e38009`) — แก้ในรีโปแล้ว ยังไม่ได้ deploy

**ผลตรวจซ้ำด้วยการรันจริง:** `supabase/tests/run.sh` บน Postgres 16 ผ่าน 80 migration และ 136 ข้อ · Deno ผ่าน 306 + 10 ข้อ และ `deno check` ทุก Edge Function (รวม `quote-create` และ `order-audit`) · `npm test` ผ่าน 30 ไฟล์ · `npm run build` ผ่าน
**ยังไม่ได้รันบน production** — ทุกอย่างด้านล่างทดสอบกับฐานจำลองที่ประกอบจาก migration ของรีโป

**ก่อนรัน SQL ใด ๆ ต้องตรวจสถานะจริงก่อน (ตรวจแล้ว 2026-11-15):** ประวัติ migration ของ production มี 60 เวอร์ชัน (ล่าสุด `20261114024149`) ไม่ตรงกับรีโป
- ไฟล์ในรีโปที่ยังไม่มีชื่อในประวัติ 18 ไฟล์ · 11-11 ถึง 11-14: `20261111180000_punpang_prune_chat_media`, `20261112100000_punpang_prune_slip_read`, `20261112110000_punpang_run_retention`, `20261113100000_punpang_retention_slipread_180`, `20261114025000_punpang_tungngern_rename`, `20261114030000_punpang_tungngern_switch`, `20261114031000_punpang_push_devices`, `20261114040000_punpang_tungngern_title`, `20261114050000_punpang_customer_push` · 11-15: `20261115000000` ถึง `20261115080000` (9 ไฟล์)
- production มี 1 เวอร์ชันที่รีโปไม่มี: `20261114024149_punpang_manee_inbox_daily_purge`
- ออบเจกต์บางอย่างมีอยู่แล้วบน production ทั้งที่ไฟล์ที่สร้างยังไม่อยู่ในประวัติ เช่น ตาราง `punpang_push_devices` (จาก `20261114031000`) → ต้องตรวจทีละออบเจกต์ และรันเฉพาะไฟล์ที่ยังไม่ได้ใช้ตามลำดับ ยังไม่ได้ตรวจการพึ่งพาระหว่างไฟล์ 11-11..11-14 กับชุด 11-15 ทีละบรรทัด (ทดสอบในเครื่องรันทั้งรีโปตามลำดับและผ่าน)

**ห้ามรัน `20261114025000_punpang_tungngern_rename` บน production:** production มีตาราง `tungngern_*` แล้วและไม่มี `manee_*` (ตรวจ 2026-11-15) ไฟล์นี้จะล้มเหลว · `20261114030000_punpang_tungngern_switch` รันซ้ำได้ปลอดภัย

**ลำดับ deploy (ทำเอง · ห้ามสลับลำดับ):**
1. ตั้งความลับ 2 ที่ให้ค่าเดียวกัน: Edge secret `PUSH_SEND_KEY` และ Vault `push_send_key` (ค่าสุ่มยาว เช่น `openssl rand -hex 32`) — ตั้งก่อน deploy `push-send` ไม่เช่นนั้นแจ้งเตือนจะหยุด (ฟังก์ชันปฏิเสธคำขอที่ไม่มีคีย์)
2. รัน SQL ตามลำดับชื่อไฟล์: `20261115000000` (ถ้ายังไม่รัน) → `20261115020000` → `20261115030000` → `20261115040000` → `20261115050000` → `20261115060000` → `20261115070000` (รันซ้ำได้ปลอดภัย) · `20261115080000` รันทีหลังสุด (ดูข้อ 6)
3. Deploy Edge Functions `push-send`, `quote-create` (ใหม่: ใบเสนอคิดราคาที่เซิร์ฟเวอร์ ต้อง deploy ก่อนหน้าเว็บ) และ `order-audit` (ใหม่: ตรวจบิลหน้าร้านและออร์เดอร์ตรงหลังบันทึก รวมการจับคู่การโอนกับ `tungngern_transfers` ที่มีอยู่แล้ว · ใช้ Edge secret `SCHEDULED_KEY` เดิม)
4. Deploy Worker `punpang-files` (ลบสลิป และอ่านรูปอ้างอิงทุกหน้า)
5. Deploy หน้าเว็บ (`src/data/store.js`, `src/views/account/AccountChat.vue`) และ build แอป Android ใหม่ (`CustomerDisplayPlugin`)
6. รัน `20261115080000_punpang_quote_server.sql` (ปิดการ INSERT ใบเสนอจากเครื่องพนักงาน) **หลังข้อ 3 และ 5 เท่านั้น** — แอปเวอร์ชันเก่าจะส่งใบเสนอไม่ได้หลังจากนี้ · `20261115090000_punpang_pos_audit.sql` รันหลังข้อ 3 ได้ (ตั้งเวลาตรวจออร์เดอร์ทุก 10 นาที ไม่กระทบการขาย) · `20261115100000_punpang_order_history.sql` รันหลัง `20261115090000` และหลังข้อ 3 (ประวัติการแก้ออร์เดอร์และแคตาล็อก ไม่กระทบการขาย)
7. ทดสอบในเบราว์เซอร์: เปลี่ยนผู้ซื้อของออร์เดอร์ที่มีคะแนน · แก้ราคา/ส่วนลดในออร์เดอร์ร่างและออร์เดอร์ที่กำลังเตรียม · แนบสลิป · รับแจ้งเตือนพนักงาน · ส่งใบเสนอแล้วตรวจว่าราคาในแชทตรงกับแคตาล็อก

**ด่านตรวจออร์เดอร์เสี่ยง (`20261115110000_punpang_order_gate.sql`) — ลำดับ deploy:** รันหลัง `20261115090000` และ `20261115100000` **และก่อนข้อ 5** (หน้าเว็บใหม่เรียก RPC `punpang_order_gate` / `punpang_review_order`) · `order-audit` (ข้อ 3) เขียนธง `hold` ซึ่งต้องมีคอลัมน์จากไฟล์นี้ก่อน (ถ้ายังไม่รัน การบันทึกผลตรวจจะล้มเหลวจนกว่าจะรัน) · ข้อ 3 และข้อ 5 ควรทำติดกัน เพราะแอปเก่าที่ไม่รู้จักด่านจะค้างการซิงก์ออร์เดอร์ที่ถูกฐานข้อมูลปฏิเสธ

**ช่องโหว่ที่ปิดในรอบนี้ (พร้อมผลทดสอบ):**
- คืนเงินเป็นคะแนนซ้ำหลังลูกค้าใช้คะแนนไปแล้ว (เดิมชำระ 1,000 บาทได้ส่วนลดรวม 2,000 บาท) → เพดานสะสมต่อออร์เดอร์ที่ตาราง `punpang_order_issued` ทดสอบ: ปฏิเสธ `cap_exceeded`
- ออกคะแนนให้ลูกค้าคนอื่นจากออร์เดอร์ของคนหนึ่ง (เดิมออร์เดอร์ 1,000 บาทออกได้ 2,000 แต้ม) → คืนเงินต้องเป็นผู้ซื้อของออร์เดอร์ (`order_customer_mismatch`)
- สิทธิ์หมุนเพิ่มซ้ำจากออร์เดอร์เดิม (เดิมเรียก 3 ครั้งได้ 15 สิทธิ์จากออร์เดอร์ 5 สิทธิ์) → โอนได้เฉพาะที่ตัดจากผู้ซื้อเดิมไว้ (`pending_*`) โอนซ้ำไม่เพิ่มของ
- ผู้ใช้แอปแก้ราคา/จำนวนรายการ ส่วนลด ค่าส่ง VAT ยอดงวดที่ชำระ ผู้ซื้อ คะแนนและคูปองที่ใช้ของออร์เดอร์ใดก็ได้ (เอกสารเดิมบรรทัด 34 ระบุว่า "ของตัวเอง" ซึ่งแคบเกินจริง) → trigger `punpang_orders_field_guard` ตรวจรายฟิลด์ตามสิทธิ์ ทดสอบ: ช่างเค้กแก้ราคาไม่ได้ · ร่างแก้ได้ · ยอดงวดที่ยืนยันแก้ไม่ได้ถ้าไม่มีสิทธิ์
- ผู้ไม่ล็อกอิน (anon) มีสิทธิ์ ALL บนตารางคลิก/push/tungngern (แม้ RLS กันแถวไว้) → เหลือ select 3 ตาราง (สินค้า ตั้งค่า รีวิว) และ RPC 4 ตัวที่หน้าร้านใช้ · ถอน TRUNCATE/REFERENCES/TRIGGER จากทุกตารางของ anon/authenticated
- Worker `/delete` ให้ผู้แจ้งชำระลบสลิปของออร์เดอร์ใดก็ได้ (ขัดกับกติกาข้อ 20 และ 53 ด้านล่าง) → ลบสลิปได้เฉพาะ `confirmPayment`/แอดมิน ทดสอบด้วย Deno
- `push-send` รับคำขอจากใครก็ได้ → ต้องมีหัว `x-push-key` ตรงกับคีย์ใน Vault (ไม่ตั้งคีย์ = ปิดทั้งหมด) ทดสอบด้วย `pushauth.test.ts`
- Worker อ่านรูปอ้างอิงได้แค่ 1,000 แถวแรกต่อตาราง (รูปที่ถูกอ้างในแถวที่ 1,001+ ถูกนับว่าไม่ถูกใช้และย้ายเข้าถังขยะได้) → อ่านทุกหน้า และหยุดลบถ้าอ่านไม่สำเร็จ ทดสอบด้วย Deno
- ตัวนับคลิกรูปเค้ก นับทั้งตารางทุกครั้งที่มีคนกด → ใช้สถิติของตาราง
- การตรวจเลขอ้างอิงการชำระซ้ำ (`data @> …`) สแกนทุกออร์เดอร์ → ดัชนี GIN
- FK `punpang_push_devices.staff_id` ไม่มีดัชนี → เพิ่มแล้ว
- Android: จอลูกค้าตรวจว่าเป็น JSON ก่อนส่งเข้า WebView และ escape สตริง · แชทลูกค้า: ลิงก์รูปผ่าน `safeHref`

- **ออร์เดอร์ที่ผลตรวจมีรายการ high ยืนยันชำระ/ส่งมอบไม่ได้จนกว่าผู้จัดการจะตรวจ (ด่านตัวเลือก B · ทำแล้วในรีโป ยังไม่ deploy):** trigger `punpang_orders_review_gate` บังคับที่ฐานข้อมูลสำหรับคำขอที่ล็อกอิน · ผู้จัดการ (สิทธิ์ `manage`) ตรวจได้ผ่าน RPC `punpang_review_order` หลังผลตรวจล่าสุดเท่านั้น · ผลตรวจใหม่ทำให้ต้องตรวจซ้ำ · บิลหน้าร้านไม่เข้าด่าน · แอปตรวจสถานะด่านก่อนยืนยันชำระ/ส่งมอบ แสดงรายการที่พบ และล็อกปุ่มที่เกี่ยวข้อง · ทดสอบ: DB C7 12 ข้อ · `src/lib/orderGate.test.mjs` 11 ข้อ · **ยังไม่ทดสอบ UI กับ Supabase จริง** (ตรวจด้วย build และตรรกะเท่านั้น)
- ส่วนลดคูปองคำนวณในแอปแล้วบันทึกลงออร์เดอร์ตรง ๆ (ทดสอบแล้ว: ตั้งส่วนลด 400 บาทจากคูปองที่ไม่มีอยู่จริงได้) → ส่วนลดในออร์เดอร์ต้องตรงกับคูปองที่จองไว้กับออร์เดอร์นั้นที่เซิร์ฟเวอร์ ทั้งตอนสร้างและตอนแก้ (ไม่เกินมูลค่าคูปองและยอดออร์เดอร์ และถึงขั้นต่ำของคูปอง) · migration `20261115050000` · ทดสอบ 10 ข้อ
- ตอนสร้างออร์เดอร์ใหม่ คะแนนที่ใช้ และส่วนลดที่ไม่ใช่ศูนย์ ใส่มาเองได้ (ทดสอบแล้ว) → คะแนนที่ใช้ต้องว่าง และส่วนลดต้องมีสิทธิ์ปรับราคา (ผู้จัดการผ่านทุกข้อ) · migration `20261115060000` · ทดสอบ 6 ข้อ
- ราคาในใบเสนอ (ตัดสินใจแล้ว: ทางเลือก A) ราคาที่ลูกค้าเห็นและตกลงคือราคาที่ใช้จริง → ข้อมูลของใบเสนอที่ส่งแล้วแก้ไม่ได้ ลูกค้า/แชทของใบเสนอเปลี่ยนไม่ได้ และออร์เดอร์จากใบเสนอต้องตรงกับใบเสนอ (รายการ VAT ค่าส่ง ลูกค้า สถานะที่ยืนยันแล้ว และแปลงซ้ำไม่ได้) · migration `20261115070000` · ทดสอบ 11 ข้อ · แอปส่ง `quoteId` ไปกับออร์เดอร์ที่สร้างจากใบเสนอ (`store.js` `quoteToOrder`/`createOrder`)
- **ราคาใบเสนอคิดที่เซิร์ฟเวอร์แล้ว** (รอบเดียวกัน): Edge Function `quote-create` คิดราคาจากแคตาล็อกด้วย `src/lib/quotePrice.js` (ชุดเดียวกับแอป ผ่าน schedlib) — ราคาสินค้าหน้าร้านจากสินค้าในระบบ (ราคาที่เครื่องส่งมาไม่มีผล) · โปรส่วนลด/บันเดิล/ดีล/ของแถมคิดที่เซิร์ฟเวอร์ (ของแถมและส่วนลดที่ส่งมาเองถูกทิ้ง) · VAT จากค่าร้าน · ร้านปิดรับนัดถูกปฏิเสธ · ตัวเลือกบนสินค้าหน้าร้านไม่มีผลต่อราคา (เหมือนการขายหน้าร้าน) · ใบเสนอใหม่สร้างได้ทางเซิร์ฟเวอร์เท่านั้น (migration `20261115080000` ปิด INSERT จาก authenticated) · ทดสอบ: ไฟล์อ้างอิง 8 เคส (`src/lib/quotePrice.golden.json`) สร้างจากโค้ดเดิมของแอป ตรงกันทุกไบต์ทั้งเวลาไทย/UTC/ลอสแอนเจลิส และหลังแยกโมดูลแล้ว · DB ทดสอบ C4 2 ข้อ · **ยังไม่ได้ทดสอบ `quote-create` กับ Supabase จริง** (ตรวจด้วย `deno check` และเทสต์ตรรกะเท่านั้น)
- **ออร์เดอร์ตรวจหลังบันทึก (ไม่บล็อกการขายหรือการสร้างออร์เดอร์):** เซิร์ฟเวอร์ตรวจทุก 10 นาทีด้วย `order-audit` + pg_cron · ราคาที่ใช้เทียบเป็นราคา ณ เวลาที่สร้างออร์เดอร์ (ย้อนจากประวัติแคตาล็อก `punpang_catalog_history`) · บิลหน้าร้าน: ราคาฐาน ตัวเลือก การคำนวณต่อรายการ ส่วนลดท้ายบิล ยอดรับชำระเท่ายอดบิล · ออร์เดอร์ตรง: คำนวณราคาใหม่ด้วยตรรกะชุดเดียวกับใบเสนอ แล้วเทียบราคาต่อชิ้น ราคาเต็ม ส่วนลด ของแถม VAT · ค่าส่งที่ไม่ได้ตั้งเองต้องตรงสูตรระยะทาง (รับที่ร้านต้องไม่มีค่าส่ง) · โอนเงินที่ยืนยันต้องมีสลิป และยอดสุทธิไม่เกินยอดบิล · ตรวจซ้ำเมื่อออร์เดอร์ถูกแก้ · ข้ามร่างและออร์เดอร์จากใบเสนอ · การโอนที่มีรหัสสุ่ม (QR) เทียบกับแจ้งเตือนเงินเข้า `tungngern_transfers` จับคู่ทีละรายการ (รหัสเดียวกัน + ยอดห่างไม่เกิน 0.01): ไม่พบแจ้งเตือน = `transfer_unmatched` (check) · พบรหัสแต่ยอดไม่ตรง = `transfer_amount_mismatch` (high) · การแก้รายการและการเงินถูกบันทึกที่ `punpang_order_changes` (ใครแก้ เมื่อไร รายการใดหาย) · ผลเก็บใน `punpang_order_audits` · ทดสอบ: บิลจริง 5 ใบและออร์เดอร์ตรง 7 เคสผ่านทั้งหมด การแก้ถูกจับ (`src/lib/posAudit.test.mjs`, `src/lib/orderAudit.test.mjs`, `src/lib/catalogHistory.test.mjs`, `_shared/*.test.ts`) · DB ทดสอบ C5 3 ข้อ และ C6 5 ข้อ

- ตัวแปร `ord` ชนกับชื่อคอลัมน์ในไฟล์ hardening ที่ยังไม่รัน (ทำให้การตัด/คืนคะแนนล้มเหลว) — แก้แล้วก่อน deploy เวอร์ชันที่รันอยู่ไม่มีบั๊กนี้
- เวอร์ชันของ `punpang_ledger_apply` ที่รันอยู่ (20261110174623) มีช่องเดียวกับข้อ 1–3 ของรอบนี้ → ควรรันไฟล์ใหม่โดยเร็ว

**ยังเหลือ (ต้องตัดสินใจหรือทำต่อ):**
- **ด่านตรวจออร์เดอร์เสี่ยง: ข้อจำกัด:** (1) ออร์เดอร์ที่เพิ่งแก้ยังไม่ถูกกั้นจนกว่ารอบตรวจ (≤10 นาที) จะรัน (2) **ตัดสินใจแล้ว: ไม่กั้นการยืนยันอัตโนมัติ (คงเดิม)** — แจ้งเตือนธนาคาร สลิปในแชท และสลิปลูกค้าเป็นคำขอ service role ไม่มี JWT · ร้านเปิดการยืนยันอัตโนมัติอยู่ (`slipQr.autoConfirm`: เปิด 3 วัน · อ่านจาก production 2026-11-15) → เมื่อ deploy ด่านแล้ว ออร์เดอร์ที่มีรายการ high ยังยืนยันชำระอัตโนมัติได้โดยไม่ผ่านผู้จัดการ แต่การส่งมอบยังกั้นจนผู้จัดการตรวจ และป้ายรายการเสี่ยงยังแสดงในออร์เดอร์นั้น (3) ไม่มีเกณฑ์ยอดหรือส่วนลด — กั้นเฉพาะรายการที่ตรวจพบว่าผิด (ตามที่เลือก) · การรับชำระแบบ POS ไม่เข้าด่าน (ตามที่เลือก)
- **ค่าส่งของใบเสนอยังรับจากเครื่องพนักงาน** (ตรวจรูปแบบและช่วงค่าเท่านั้น): ผู้สร้างออร์เดอร์ตั้งค่าส่งเองได้ตามการออกแบบเดิม (`feeManual`) · ถ้าต้องการล็อก ต้องคิดค่าส่งจากระยะทางและตั้งค่าร้านที่เซิร์ฟเวอร์ด้วย
- **ออร์เดอร์ยังไม่ถูกบังคับที่ฐานข้อมูล:** การตรวจเป็นการเตือนหลังบันทึก ไม่ได้ป้องกัน (การป้องกันต้องเปลี่ยนวิธีสร้างออร์เดอร์ ยังไม่ทำ) · การลบรายการถูกบันทึกแล้วแต่ไม่ได้บล็อก · ไม่ตรวจคะแนนและคูปอง (ตรวจตอนบันทึกแล้ว) · การชำระตรวจเฉพาะภายใน (สลิปโอนเงิน ยอดสุทธิเกินยอดบิล) ยังไม่เทียบกับเงินเข้าบัญชีจริง (ต้องเชื่อมธนาคาร ยังไม่ทำ) · ไม่ตรวจโปรโมชันที่ขึ้นกับช่วงเวลาซ้ำ และไม่รู้ว่ารับเงินจริง · ประวัติแคตาล็อกเริ่มนับตั้งแต่ deploy migration นี้ ราคาที่เปลี่ยนก่อนหน้านั้นไม่มีบันทึก ออร์เดอร์เก่าที่ราคาเปลี่ยนไปแล้วจึงอาจถูกรายงานให้ดู
- หน้าร้าน (POS) ยังจองคูปองด้วยรหัสชั่วคราว `pos-pending` ก่อนสร้างบิล และใช้ซ้ำได้ในขั้นจอง (ยอมรับไว้เพราะแอปเดิมทำแบบนี้) — ควรเปลี่ยนให้จองด้วยรหัสบิลจริง
- **ราคาต่อรายการตอนสร้างออร์เดอร์ยังไม่ถูกตรวจ (ตรวจหลังบันทึกแล้ว ยังไม่บังคับตอนสร้าง):** ทดสอบฐานข้อมูลแล้ว พนักงานขายตั้งราคา 1 บาทได้ ข้อเสนอ: ให้เซิร์ฟเวอร์คิดราคาออร์เดอร์ตรงด้วยโมดูลเดียวกับใบเสนอ (`src/lib/quotePrice.js` ผ่าน schedlib — ใบเสนอใช้แล้ว) ผ่าน Edge Function สร้างออร์เดอร์ แล้วปิดการ INSERT ตรงจากแอป · ต้องทดสอบกับหน้าสร้างออร์เดอร์และหน้าขายจริง
- การโอนที่ไม่มีรหัสสุ่ม (กรอกยอดเอง) ไม่ถูกจับคู่กับแจ้งเตือนเงินเข้า · แจ้งเตือนที่เข้าหลังรอบตรวจจะไม่ถูกตรวจซ้ำจนกว่าออร์เดอร์จะถูกแก้ (`transfer_unmatched` อาจค้างเป็นข้อให้ดู)
- ยืนยันสลิปอัตโนมัติ (ปิดเป็นค่าเริ่มต้น): ยืนยันจากภาพ OCR ที่ลูกค้าส่งเอง ยังไม่ตรวจกับธนาคาร — ควรตรวจก่อนเปิดใช้
- การเปลี่ยนผู้ซื้อยังเรียกจากแอป ระบบจำกัดยอดที่โอนได้ แต่ยังไม่บังคับว่าผู้ซื้อของออร์เดอร์เปลี่ยนจริงในธุรกรรมเดียวกัน
- ผู้มีสิทธิ์สร้างออร์เดอร์ยังแก้ข้อมูลลูกค้าได้ตามสิทธิ์เดิม (เช่น เบอร์โทร) — ไม่กระทบการเข้าสู่ระบบของลูกค้า
- การนับคลิกเป็นค่าประมาณจากสถิติของ Postgres (autovacuum ปรับให้เอง)
- Supabase ให้สิทธิ์เริ่มต้นกับ anon/authenticated ทุกฟังก์ชันใหม่ — migration ถัดไปต้องถอนสิทธิ์เองเสมอ
- ดัชนี GIN ถูกสร้างในไฟล์ migration (บล็อกการเขียนชั่วคราว) — ตารางออร์เดอร์ตอนนี้เล็ก หากโตมากควรสร้างแบบ `CONCURRENTLY` นอก migration
- ลดสิทธิ์ของพนักงานขายชั่วคราว (เช่น ถอน `changeBuyer`/`useLoyalty`) ก่อนรันไฟล์ใหม่ เป็นการตัดสินใจทางธุรกิจ ไม่ได้ทำในโค้ด

## ยังเหลือ (ต้องตัดสินใจ/ทดสอบก่อน)
- **บอท AI (ยังไม่ deploy):** คีย์ `ANTHROPIC_API_KEY` ต้องเป็น Supabase secret เท่านั้น (ตั้งผ่านฟอร์มที่ปลอดภัย ห้ามวางในแชท/โค้ด/log) · ส่งให้โมเดลเฉพาะข้อความปัจจุบันของลูกค้า (ไม่มีประวัติแชท/ชื่อ/ข้อความพนักงาน) และข้อมูลร้าน/สินค้าสาธารณะ · ข้อความที่ `scrubPII` พบเบอร์/อีเมล/เลขออร์เดอร์/เลขยาว หรือมีชื่อลูกค้า จะไม่ส่งเลย · การจับชื่อที่ลูกค้าพิมพ์เองโดยไม่รู้จักชื่อไม่ได้ 100% จึงยังมีความเสี่ยงเล็กน้อย · เพดานต่อวันกันค่าใช้จ่ายเกิน · aiLog เก็บข้อความลูกค้าตัด 200 ตัวอักษร (ต้องกำหนดอายุข้อมูลตามนโยบาย PDPA) · migration `punpang_ai_take` ยังไม่ได้ apply

- **Leaked Password Protection**: เปิดเองที่ Supabase Dashboard → Authentication → Providers → Email
- **แต้มสะสม**: ตัดแต้มยังทำฝั่งแอป (ป้องกันการเขียนทับด้วยเทียบเวอร์ชันแล้ว) · ทางที่ถูกคือตารางรายการแต้มแบบเพิ่มอย่างเดียว ให้เซิร์ฟเวอร์คิดยอดคงเหลือ
- **`fb-webhook` / `fb-send` / `fb-connect`** (กระทบทุกข้อความของเพจ ต้องทดสอบกับบัญชี Messenger ทดสอบก่อน deploy):

  - `fb-send`: จำกัดโดเมนลิงก์การ์ด (ต้องรู้โดเมนใช้งานจริงก่อน), rate limit ต่อคน, กันส่งซ้ำ
  - `fb-connect`: ลบ page token ค้างหลัง OAuth ไม่สำเร็จ
- **สิทธิ์เขียนคอลเลกชัน `consents`/`outbox`** ใน `punpang_rec_can` ยังเปิดให้พนักงานทุกคน (`outbox` จำเป็นต่อการแจ้งเตือนจากทุกบทบาท) ต้องไล่ดูทีละบทบาทก่อนจำกัด
- `punpang_click_pairs` / `punpang_record_click` เรียกโดย anon ได้ตามการออกแบบ (คำนวณรูปแนะนำ) ข้อมูลเป็นแฮช
