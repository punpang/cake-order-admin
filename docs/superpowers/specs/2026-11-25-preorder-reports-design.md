# สั่งล่วงหน้า: รายงานสำหรับร้าน — Design

วันที่: 2026-11-25 · สถานะ: รอการอนุมัติ

## 1. เจตนา (Intent)
ร้านมีออเดอร์สั่งล่วงหน้าแล้ว แต่ยังไม่มีรายงานที่บอกว่าต้องเตรียมสินค้าเท่าไรและวันไหน ใครต้องรับของวันนี้ ของต้องส่งอะไรบ้าง และยอดที่ยังค้าง พนักงานต้องนับเองจากรายการออร์เดอร์ ซึ่งเสี่ยงผิดพลาด ต้องการให้ระบบสรุปให้ถูกต้องและพิมพ์ได้

## 2. เป้าหมาย / ไม่ใช่เป้าหมาย / ต้องไม่เกิด
- **เป้าหมาย:** มี 6 รายงาน (ดูข้อ 5) ที่นับถูกต้องจากข้อมูลจริง · พิมพ์หรือดูบนมือถือได้
- **ไม่ใช่เป้าหมาย:** ส่งออกไฟล์ Excel · กราฟ · การแจ้งเตือน (อยู่ในแผนแยก) · เปลี่ยนการคิดยอดหรือบัญชี
- **ต้องไม่เกิด:** นับออร์เดอร์ที่ยกเลิกหรือหมดเวลาแล้ว · เห็นข้อมูลลูกค้าเกินกว่าที่ใช้ทำงาน · รายงานต่างจากหน้าออร์เดอร์ที่ใช้ข้อมูลเดียวกัน

## 3. ข้อจำกัด (Constraints)
- ผู้ที่ดูรายงานต้องมีสิทธิ์จัดการสั่งล่วงหน้า (`managePreorder`) เท่านั้น
- การคำนวณทำที่เซิร์ฟเวอร์ (Edge Function `preorder-admin`) ไม่เชื่อค่าจากหน้าจอ
- **กติกาการนับ (ตกลงแล้ว):** ใบจัดเตรียมนับทุกออร์เดอร์ที่ยังไม่ยกเลิกและไม่หมดเวลา และแสดงสถานะการชำระแยกให้เห็น
- ข้อมูลลูกค้าในรายงานแสดงเฉพาะชื่อและเบอร์ที่จำเป็นต่อการรับของ

## 4. แนวทาง (Approaches)
| ทาง | แนวทาง | ข้อดี | ข้อเสีย |
|---|---|---|---|
| **A (เลือก)** | action ใหม่ `reports` ใน `preorder-admin` คืนข้อมูลรวมที่คำนวณแล้ว + ฟังก์ชันล้วนใน `src/lib/preorderReports.js` (มีเทสต์) สำหรับการจัดกลุ่ม | ยอดตรงกับหน้าออร์เดอร์ ทดสอบได้ง่าย | ต้องแก้ Edge Function และ Release |
| B | คำนวณในหน้าเว็บจากรายการออร์เดอร์ที่โหลดอยู่ | ไม่ต้อง Release | ถ้าโหลดไม่ครบจะนับผิด และไม่เหมาะกับข้อมูลจำนวนมาก |
| C | สร้าง View ในฐานข้อมูล | เร็วและตรงกับข้อมูลจริง | ต้อง migration และแก้สิทธิ์ของ view |

**เลือก A** เพื่อให้นับถูกต้องจากเซิร์ฟเวอร์เดียว และหลีกเลี่ยงการนับผิดจากข้อมูลไม่ครบ

## 5. การออกแบบ (How)
รายงาน 6 รายการ อยู่ในแท็บ "รายงาน" ของหน้าสั่งล่วงหน้า:
1. **ใบจัดเตรียม:** สินค้า × จำนวนรวม × วันรับ แยกตามวันรับ พร้อมสถานะการชำระต่อออร์เดอร์
2. **รายการรับของประจำวัน:** ชื่อลูกค้า เวลา วิธีรับ ยอดค้างชำระ (เลือกวันได้)
3. **รายการจัดส่งพัสดุ:** ที่ยังไม่ส่ง พร้อมค่าไปรษณีย์และเลขพัสดุ (ถ้ามี)
4. **ยอดค้างชำระ:** ออร์เดอร์ที่จ่ายไม่ครบ เรียงตามวันหมดเวลา
5. **สรุปรายแคมเปญ:** ยอดขาย มัดจำ โควตาที่จองและที่เหลือ
6. **ยกเลิก หมดเวลา คืนเงิน:** รายการพร้อมยอดที่คืน

**การแสดงผล:** ตารางบนมือถือเป็นการ์ดต่อรายการ · กดพิมพ์ได้ด้วย CSS สำหรับพิมพ์ (ไม่มีเมนูที่ติดมาในงานพิมพ์)

## 6. การตัดสินใจที่ผมเลือกเอง (แก้ได้)
- แท็บ "รายงาน" อยู่หลังแท็บ "ออร์เดอร์"
- ทุกรายงานมีตัวกรองแคมเปญและช่วงวันรับ
- เลขในรายงานต้องตรงกับหน้าออร์เดอร์และหน้าบัญชี (ทดสอบเทียบกัน)
- ทำหลัง PR #161 และ Release เสร็จ เพื่อไม่ให้แก้ไฟล์ชนกับงานการแจ้งเตือน

## 7. การตรวจสอบ
- Node: ฟังก์ชันจัดกลุ่มและการนับ (รวมกรณีออร์เดอร์ยกเลิก หมดเวลา และชำระบางส่วน)
- Deno: action `reports` คืนข้อมูลตามสิทธิ์และไม่คืนข้อมูลเกิน
- e2e: แท็บรายงานแสดงตัวเลขตรงกับออร์เดอร์ตัวอย่าง
- `npm test` · `npm run test:fn` · build และ bundle (ถ้าเกินเพดาน หยุดและขออนุมัติ)

## 8. ผลกระทบการ deploy
- แก้ Edge Function `preorder-admin` (ไม่มี migration) ต้อง Release ชุดใหม่บน production พร้อมอนุมัติ environment
- งานนี้ต้องรอ PR #161 merge ก่อน
