# ดีไซน์: ระบบ "สั่งล่วงหน้า" (preorder)

สถานะ: ผู้ใช้อนุมัติแนวทางและดีไซน์ระดับแผนแล้ว (2026-11-24) · เอกสารนี้ใช้เป็นฐานของแผนลงมือ
ผู้ใช้: เจ้าของร้านเค้ก (แอปแอดมินร้าน + หน้าเว็บลูกค้า) · โปรเจกต์: Vue + Supabase (`/home/user/cake-order-admin`)

## 1. ความตั้งใจ (Intent)
ร้านต้องการเปิดรับสั่งสินค้าล่วงหน้าเป็นช่วงๆ (แคมเปญ) โดยให้**ลูกค้ากดสั่งเองบนเว็บ** จ่ายมัดจำอย่างน้อย 50% จึงนับว่าสั่งสำเร็จ และร้านต้องได้รายงานเตรียมสินค้าที่ละเอียดแม่นยำ
ผู้ใช้ไม่ได้ระบุเหตุผลเชิงธุรกิจเพิ่ม แต่เป้าหมายที่ชัดคือ: ควบคุมกำลังผลิตต่อวัน ลดภาระการรับออร์เดอร์ทางแชท และรู้ล่วงหน้าว่าต้องเตรียมอะไรวันไหนเท่าไร

## 2. Goals
1. ร้านตั้งแคมเปญ: ช่วงวันเริ่ม-สิ้นสุดรับสั่ง · ช่วงวันรับสินค้า · โควตา · สินค้าที่ร่วมรายการ (เลือกจากสินค้า POS `retailItems`) · โปรโมชั่นราคา · บันเดิ้ลเฉพาะแคมเปญ · % มัดจำขั้นต่ำ (ค่าตั้งต้น 50) · เวลากำหนดจ่ายก่อน
2. โควตานับ **ต่อสินค้าต่อวันรับ + ยอดรวมต่อวัน** (ผู้ใช้เลือก) ลูกค้าเห็นจำนวนที่ว่างเหลือตอนเลือกวัน
3. ลูกค้า**ไม่ต้องเป็นสมาชิกมาก่อน** กรอกชื่อ+เบอร์ ยืนยันเบอร์ด้วย OTP แล้วระบบสร้างลูกค้าให้อัตโนมัติ (ผูกความยินยอม PDPA)
4. สั่งแล้วได้ QR ถุงเงิน (ยอด ≥ มัดจำ) ช่องทางชำระ: QR ถุงเงินออนไลน์ยืนยันอัตโนมัติ · เงินสดหน้าร้าน (ลูกค้าเลือก "จ่ายหน้าร้าน" ร้านกดรับเงิน)
5. "สั่งสำเร็จ" = ยอดที่ยืนยันแล้ว ≥ มัดจำขั้นต่ำของแคมเปญ
6. **การจองโควตา:** จองทันทีที่กดสั่ง จนถึงเวลากำหนดจ่าย เลยแล้วปล่อยโควตา แต่เก็บออร์เดอร์ไว้ ลูกค้าต้องขอขยายเวลา ร้านอนุมัติ → จองโควตากลับถ้ายังว่าง ถ้าเต็มแล้วแจ้งลูกค้า
7. เงินเข้าบัญชีอัตโนมัติเหมือนออร์เดอร์ปกติ (มัดจำ → รายได้รับล่วงหน้า 2300, รับรู้รายได้และภาษีขายตอนส่งมอบ, ยกเลิกแล้วริบ → 4900)
8. รายงานเตรียมของ: วันรับ × สินค้า × จำนวน แยก จ่ายมัดจำแล้ว/รอมัดจำ/ยอดค้าง พร้อมที่ว่างเหลือ และพิมพ์ได้
9. มีทั้งฝั่งร้าน (ตั้งแคมเปญ จัดการออร์เดอร์) และฝั่งลูกค้า (สั่ง จ่าย ขอขยาย ดูสถานะ) · สถานะคล้ายออร์เดอร์ปกติ
10. **แยกจาก POS/ออร์เดอร์ปกติ** (ผู้ใช้เลือกแนวทางตารางแยกทั้งชุด)

## 3. Non-goals และ Anti-goals
- ไม่แตะเส้นทาง POS และออร์เดอร์ปกติที่ใช้งานอยู่ (ห้ามกระทบการขายหน้าร้าน)
- ใบกำกับภาษีเต็มรูปของ preorder **ทำในเฟส 4 พร้อมบัญชี** (ผู้ใช้ตัดสิน) ใบกำกับเดิมผูกกับออร์เดอร์ปกติ ต้องขยายระบบใบกำกับ/Edge Function `tax-invoice`/กติกาช่วงเวลาให้รองรับ preorder — เฟส 1–3 ยังไม่มี
- ไม่ทำโปรแกรมแต้ม/คูปองสมาชิกกับ preorder รอบแรก
- Anti-goal: ระบบถือว่าล้มเหลวถ้าโควตาเกินจากการสั่งพร้อมกัน, ถ้าใครจองโควตาได้โดยไม่ยืนยันเบอร์ด้วย OTP, หรือถ้าตัวเลขบัญชีของ preorder ไม่ตรงกับเงินที่รับจริง

## 4. ข้อจำกัดที่พบจากโค้ดปัจจุบัน (ผลสำรวจ)
- ฝั่งลูกค้า**ไม่มีการสั่งเอง**: หน้าร้าน `StoreHome/StoreMenu/StoreItem` ดูอย่างเดียว ออร์เดอร์ทุกใบพนักงานสร้างผ่าน `order-create` (ต้องโทเค็นพนักงาน) `customer-order` ไม่มี action สร้างออร์เดอร์ → ต้องมี Edge Function สาธารณะใหม่
- คำว่า "campaign" ใช้กับประกาศ/โฆษณาแล้ว (`src/lib/campaigns.js`, `ManageCampaigns.vue`, ฟังก์ชัน `campaign`) → ตั้งชื่อ `preorder` / `preorderCampaigns`
- โควตาเดิม `orderCap.js` นับ "ใบออร์เดอร์ต่อวัน" ค่าเดียวทั้งร้าน และ**ไม่ atomic** (อ่านแล้ว insert ใน `order-create/index.ts:147-197`) · ออร์เดอร์ที่ไม่จ่ายถูกนับค้าง เพราะเลยกำหนดแล้ว**ไม่ยกเลิกอัตโนมัติ**
- มัดจำเดิม: `shop.depositPercent` ค่าเดียวทั้งร้าน ไม่มีด่าน "ต้องจ่ายมัดจำก่อนถึงนับ" (`confirmUnpaid` ข้ามได้)
- ขอขยายเวลา: ลูกค้าขอได้เมื่อ**เลยกำหนดแล้ว**เท่านั้น (`customer-order/index.ts:68`) ตรงกับกติกาที่ผู้ใช้ต้องการ
- ถุงเงิน: QR Biller สร้างในเบราว์เซอร์ (`promptpay.js`); Ref2 ฝั่งออนไลน์ `ORD`+12 หลัก + suffix 5 ตัว, POS ใช้ `POS`+...; ตัวรับ `tungngern-receiver` จับคู่ด้วย `ref`+`amount` ใน `_shared/notifyconfirm.ts` (`applyNotifyPayment`) ซึ่งหา order ที่ `payments[].qrRef` ตรงกัน
- โปรโมชั่นราคาเดิม: `posDiscounts/posBundles/posDeals` (`src/lib/posPromo.js`, `ManagePromos.vue`) มี `schedule` แต่**ไม่มีฟิลด์ผูกแคมเปญ** · `db.bundles` เดิมเป็นส่วนลดตัวเลือกเค้กสั่งทำ ไม่เกี่ยวกับ retailItems
- ตัวตรวจราคา `order-audit` + `punpang_orders_review_gate` ติดธง high ถ้าราคาไม่ตรงแคตาล็อก (ไม่เกี่ยวกับ preorder ถ้าใช้ตารางแยก แต่ต้องมีตัวตรวจของตัวเอง)
- ระบบมีกติกาเฉพาะที่ต้องตามเมื่อเพิ่มตารางใหม่: `punpang_test_sync` ต้องจัดประเภทตาราง (ไม่งั้นโหมดทดสอบล้ม), สำเนา schedlib ต้องซิงก์ด้วย `scripts/sync-schedlib.mjs` (มีเทสต์บังคับ), งบ bundle รวม 904 KB (หน้าใหม่ต้อง lazy-load), CI รัน `test:fn` / `test:db` / e2e (`e2e/_routes.mjs`)
- การสั่งซื้อต้องมีเบอร์ลูกค้า (`chatOrderBlock`) และยินยอม PDPA (`_shared/consent.ts`); มี rate limit (`_shared/ratelimit.ts`), Turnstile (`src/lib/turnstile.js`), โหมดทดสอบ (`refuseInTest`)

## 5. แนวทางที่พิจารณา
- **A (ผมแนะนำ แต่ผู้ใช้ไม่เลือก):** ออร์เดอร์ปกติ + ธง `preorder` ใช้ระบบชำระ/ขยายเวลา/ถุงเงิน/บัญชีเดิม งานเล็กกว่า 2–3 เท่า ข้อแลกเปลี่ยนคือต้องแตะระบบออร์เดอร์เดิม (order-audit ต้องรู้จักราคาแคมเปญ)
- **B (ผู้ใช้เลือก):** ตารางและฟังก์ชันแยกทั้งชุด แยกขาดจากออร์เดอร์เดิม ข้อแลกเปลี่ยน: ต้องสร้างซ้ำการชำระ จับคู่ถุงเงิน ขอขยายเวลา แจ้งเตือน บัญชี; ลดความเสี่ยงโดยนำ**ฟังก์ชันล้วนเดิม**มาใช้ซ้ำ (`payDue.js`, `promptpay.js`, `posPromo.js`, `_shared/notifyconfirm.ts`, `acct/derive.js`)
- ตัดทิ้ง: ให้พนักงานสร้างออร์เดอร์จากแคมเปญ (ขัดกับที่ผู้ใช้เลือกให้ลูกค้าสั่งเอง)

## 6. ส่วนที่ผู้ใช้ตัดสินใจ
ลูกค้ากดสั่งเองบนเว็บ · จองโควตาถึงเวลาจ่ายแล้วปล่อย · โควตาต่อสินค้าต่อวันรับ + ยอดรวมต่อวัน · ไม่ต้องเป็นสมาชิก ยืนยันเบอร์ด้วย OTP แล้วสร้างลูกค้าอัตโนมัติ · ตารางแยก (B) · เข้าบัญชีอัตโนมัติ
ผู้ใช้ย้ำเองด้วยว่า "ลูกค้าทุกคนสั่งได้โดยไม่ต้องเป็นสมาชิกมาก่อน" (แก้จากเดิมที่ผมสรุปว่าต้องล็อกอิน)
ผู้ใช้ตัดสินเพิ่ม (ปิดประเด็นค้างเดิม):
- **ยกเลิกออร์เดอร์ที่สั่งสำเร็จแล้ว:** ร้านเลือกเองตอนยกเลิกแต่ละใบ (คืนเต็ม/บางส่วน/ไม่คืน) ยอดที่ไม่คืนถือเป็นริบและลงบัญชี 4900 ลูกค้ายกเลิกเองไม่ได้ ต้องติดต่อร้าน (ใช้แบบเดียวกับยกเลิกออร์เดอร์เดิม: เลือกช่องทางคืน ส่วนที่เหลือคือริบ) ยกเลิกแล้วต้องคืนโควตาอัตโนมัติ
- **เวลากำหนดจ่ายมัดจำ:** ไม่มีค่าตั้งต้น ร้านต้องกรอกทุกแคมเปญ (ฟอร์มตั้งแคมเปญบังคับกรอก บันทึกไม่ได้ถ้าว่าง)
- **ใบกำกับภาษีเต็มรูป:** ทำในเฟส 4 พร้อมบัญชี

## 7. ส่วนที่ผมตัดสินเอง (ผู้ใช้ตรวจได้)
- เงินสด = ลูกค้าเลือก "จ่ายหน้าร้าน" ร้านกดรับ (ใช้ `receivePaymentNow` แนวเดิม)
- ชื่อโมดูล `preorder` · เลขที่ `PRE-ddmmyy-xxxxxx` · Ref2 ของ QR ขึ้นต้น `PRE`
- สถานะใช้ชุดเดียวกับออร์เดอร์ปกติ (awaiting_payment → payment_confirmed → preparing → prepared → delivered/รับแล้ว, cancelled) · "เลยกำหนดแล้วปล่อยโควตา" เป็นธงบนออร์เดอร์ ไม่ใช่สถานะใหม่
- โปรโมชั่น/บันเดิ้ลของแคมเปญเก็บในแคมเปญเอง (ไม่ปะปนกับ `posDiscounts`) และคำนวณด้วยฟังก์ชันล้วนเดียวกับที่เซิร์ฟเวอร์ใช้ตรวจราคา

### 7.1 ข้อที่ผู้ตรวจถามและผมตัดสินเอง (ตรวจได้)
1. **ตัวเลขโควตา:** มี 2 ตัวเลขที่ตั้งแยกกันได้ และ**ตั้งหรือไม่ตั้งก็ได้**: เพดานต่อสินค้าต่อวันรับ (ไม่ตั้ง = ไม่จำกัดรายตัว) และเพดานรวมต่อวัน (เป็นตัวเลขของมันเอง ไม่ใช่ผลรวมของเพดานรายตัว) · บันเดิ้ลนับโควตาตาม**จำนวนชิ้นของสินค้าแต่ละตัวในชุด** · ตาราง `punpang_preorder_slots` มี 1 แถวต่อ (แคมเปญ, วันรับ, สินค้า) และ 1 แถวพิเศษต่อวัน (สินค้า = null) สำหรับยอดรวม และ RPC จองต้องล็อกทั้งแถวสินค้าและแถวรวมในธุรกรรมเดียว
2. **การชำระและ "สั่งสำเร็จ":** ลูกค้าจ่ายเป็นงวดได้ (ตามโครงสร้าง `payments[]` เดิม) งวดแรกที่ยืนยันแล้วต้องรวม ≥ มัดจำขั้นต่ำจึงนับว่าสำเร็จ ลูกค้าเลือกยอดที่จ่ายได้ (≥ ที่ต้องจ่าย) QR สร้างใหม่ต่องวด ส่วนที่เหลือจ่ายภายหลังและต้องครบก่อนส่งมอบ/รับสินค้า (ตรงกับกติกาเดิม "ส่งมอบต้องชำระครบ") บัญชีรับมัดจำเข้า 2300 ตามยอดที่ยืนยันแล้ว
3. **ออร์เดอร์เงินสด:** ใช้เวลากำหนดจ่ายเท่ากับ QR ถ้าร้านยังไม่ได้รับเงินสดภายในเวลานั้น โควตาถูกปล่อยเหมือนกัน
4. **ขอขยายเวลา:** ลูกค้าขอได้ทุกครั้งที่เลยกำหนดและไม่มีคำขอค้าง (เหมือนระบบเดิม) ร้านกำหนดเวลาใหม่เอง ตอนอนุมัติระบบพยายามจองโควตากลับแบบ atomic ถ้าเต็มจะ**บล็อกการอนุมัติ**และแจ้งร้านให้ปฏิเสธหรือแจ้งลูกค้าเปลี่ยนวันรับ ลูกค้าได้รับแจ้งผลทุกกรณี
5. **เซสชันหลัง OTP:** ใช้เซสชันลูกค้าแบบเดียวกับ `customer-auth` แต่จำกัดขอบเขตให้เห็นเฉพาะออร์เดอร์ preorder ของตัวเอง ไม่ใช่ข้อมูลบัญชีสมาชิกทั้งหมด
6. **เบอร์ที่มีอยู่แล้ว:** OTP พิสูจน์ว่าเป็นเจ้าของเบอร์ จึงผูกกับลูกค้าเดิมได้ แต่ก่อนยืนยันห้ามแสดงข้อมูลใดๆ ของลูกค้านั้น และเซสชันที่ได้เห็นเฉพาะ preorder ตามข้อ 5
7. **ส่วนลดซ้อนกัน:** ไม่ซ้อน — คิดบันเดิ้ลก่อน แล้วแต่ละรายการได้ส่วนลดของแคมเปญ**ตัวที่ให้ราคาต่ำสุดเพียงตัวเดียว** (กติกาง่าย ตรวจย้อนและตรวจฝั่งเซิร์ฟเวอร์ได้)
- ตัดสินเองโดยไม่ถาม: ไม่มีช่วงเวลารับย่อยภายในวัน (มีแค่วัน) · หน้า preorder ใช้โครงหน้าร้านเดิม

## 8. สถาปัตยกรรมโดยย่อ
- **ฐานข้อมูล:** `punpang_preorder_campaigns` · `punpang_preorder_orders` (data jsonb: รายการ วันรับ ยอด payments[] ขยายเวลา ธงโควตา) · `punpang_preorder_slots` (แคมเปญ × วันรับ × สินค้า → จำนวนที่จอง) · RPC `punpang_preorder_reserve/release` ล็อกแถวแบบ atomic · RLS/guard · จัดประเภทตารางใน `punpang_test_sync`
- **Edge Function `preorder`:** สาธารณะ แต่ก่อนจองต้องยืนยันเบอร์ด้วย OTP (ใช้กลไก OTP/SMS ของ `customer-auth` + `sms-send`) แล้วสร้าง/ผูกลูกค้าอัตโนมัติ และออกเซสชันหรือลิงก์ออร์เดอร์ · actions: campaigns / otp_request / otp_verify / quote / create / pay / qr_request / read_slip / extend / state · ตรวจราคา/โควตา/ช่วงรับสั่ง/มัดจำที่เซิร์ฟเวอร์ · rate limit ต่อเบอร์/IP + Turnstile
- **ถุงเงินอัตโนมัติ:** ขยาย `_shared/notifyconfirm.ts` ให้จับคู่ qrRef `PRE...` กับการชำระของ preorder; ยืนยันอัตโนมัติเมื่อยอด ≥ มัดจำหรือตรงงวด
- **งานตามเวลา:** ขยาย `scheduled` (`_shared/scheduled/plan.ts`) ปล่อยโควตาเมื่อเลยกำหนด · เตือนก่อนครบกำหนด
- **บัญชี:** ขยาย `src/lib/acct/derive.js` ให้อ่านออร์เดอร์ preorder
- **หน้าร้าน:** ManagePreorders (ตั้งแคมเปญ) · รายการ/รายละเอียดออร์เดอร์ preorder (ยืนยัน รับเงินสด อนุมัติขยาย ยกเลิก) · รายงานเตรียมของ+พิมพ์
- **หน้าลูกค้า:** หน้าแคมเปญ/สั่งซื้อ · ออร์เดอร์ของฉัน (จ่าย QR+สลิป ขอขยายเวลา)
- สิทธิ์ใหม่ `managePreorder` · event แจ้งเตือนใหม่ (+ซิงก์ schedlib) · workflow deploy `preorder` และเพิ่มใน `test:fn`

## 9. ขนาดงานและเฟส
โครงการใหญ่ ส่งใช้ได้ทีละเฟส:
1. ฐานและโควตา: migration + RPC โควตา + หน้าตั้งแคมเปญ + เทสต์ DB
2. ลูกค้าสั่งเอง: Edge Function + หน้าลูกค้า + ตรวจราคา (โปร/บันเดิ้ล)
3. ชำระและเวลา: QR/ถุงเงินอัตโนมัติ + เงินสดหน้าร้าน + ขยายเวลา + ปล่อยโควตาตามเวลา
4. บัญชี ใบกำกับภาษีเต็มรูป รายงาน แจ้งเตือน

## 10. ความเสี่ยง
โควตา race · OTP abuse/จองเล่น (OTP + rate limit + Turnstile + เพดานรอบ OTP ต่อวัน) · ค่า SMS ต่อลูกค้าใหม่ · งบ bundle · บัญชีไม่ตรงถ้า derive ผิด · ลำดับ deploy migration → ฟังก์ชัน → เว็บ

## 11. การตรวจสอบเมื่อสร้าง
เทสต์ SQL (โควตา atomic, RLS, test-mode sync) · Deno เทสต์ฟังก์ชัน · node เทสต์ lib/store (ราคา โควตา มัดจำ derive) · e2e ลูกค้าสั่ง→จ่าย→ร้านเห็นในรายงาน · `npm test` + `npm run build` + bundle budget · ทดสอบบนโหมดทดสอบก่อนเปิดจริง

## 12. ยังไม่ตัดสิน (ฝากผู้สร้าง/ถามผู้ใช้ภายหลัง)
