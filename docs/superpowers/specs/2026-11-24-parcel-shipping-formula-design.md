# สูตรค่าส่งพัสดุ (สั่งล่วงหน้า) — Design

วันที่: 2026-11-24 · สถานะ: รอการอนุมัติ

## 1. เจตนา (Intent)
ลูกค้าที่สั่งล่วงหน้าแบบพัสดุต้องเห็นค่าส่งเป็นบรรทัดเดียวที่ถูกต้องและอธิบายได้ ค่าส่งนี้มาจากสามส่วนที่ร้านควบคุมเอง เพื่อให้ราคาสะท้อนต้นทุนจริงของกล่องและการขนส่ง โดยไม่ให้ลูกค้าเห็นรายละเอียดภายใน

## 2. เป้าหมาย / ไม่ใช่เป้าหมาย / ต้องไม่เกิด
- **เป้าหมาย:** ยอดค่าส่ง = ค่าธรรมเนียมร้าน + ค่ากล่อง + ค่าส่งจากตาราง · ร้านตั้งค่าได้ทั้งหมด · เซิร์ฟเวอร์เป็นผู้คิดยอดเสมอ
- **ไม่ใช่เป้าหมาย:** เชื่อมต่อ API ขนส่ง (ไม่มี connector) · แยกโซนจังหวัด (ตัดสินแล้วว่าอัตราเดียวทั่วประเทศ) · ส่งในเมือง
- **ต้องไม่เกิด:** ลูกค้าเห็นรายการกล่อง/น้ำหนัก · ค่าส่งถูกคำนวณจากค่าที่ client ส่งมา · ออเดอร์ได้ราคาโดยไม่มีตารางรองรับ (เดาราคา) · แก้ตารางแล้วยอดของออเดอร์เก่าเปลี่ยน

## 3. ข้อจำกัด (Constraints)
- ยอดทั้งหมดต้องคิดในแหล่งเดียวกับ `preorderPrice.js` / `orderTotals` (ไม่คำนวณซ้ำ)
- สินค้าทุกชิ้นในแคมเปญส่งพัสดุต้องมีน้ำหนักและขนาด (กติกาเดิม)
- งบ bundle ปัจจุบัน 923 KB

## 4. ทางเลือก (Approaches)
| ทาง | แนวทาง | ข้อดี | ข้อเสีย |
|---|---|---|---|
| **A (เลือก)** | ค่ากล่องแยกเป็นบรรทัดของตัวเอง · ค่าส่งจากตารางสองมิติ (กล่อง × ขั้นน้ำหนัก) | ตรงกับที่ร้านกรอกราคากล่องและอัตรารายขั้นได้ตรง ๆ · ตรวจง่าย | ต้องกรอกตารางให้ครบทุกช่อง |
| B | รวมค่ากล่องไว้ในตารางค่าส่ง | กรอกช่องเดียว | ซ้ำซ้อน ค่ากล่องเปลี่ยนต้องแก้ตารางทุกช่อง |
| C | เรียก API ขนส่งหาราคาจริง | แม่นยำ | ไม่มี connector และเกินขอบเขต |

**เลือก A** เพราะตรงกับที่ผู้ใช้อธิบาย และไม่ต้องพึ่งบริการภายนอก

## 5. การออกแบบ (How)
**เลือกกล่อง:** รวมปริมาตรสินค้า = Σ(ปริมาตรชิ้น × จำนวน) → เลือกกล่องที่เล็กที่สุดที่มี `volumeCm3 ≥ ปริมาตรรวม` · ถ้าไม่มี → ปฏิเสธออเดอร์
**น้ำหนักที่ใช้ตาราง:** น้ำหนักสินค้ารวม + `boxG` ของกล่องที่เลือก
**ค่าส่ง:** หาช่อง `rates[กล่อง]` ขั้นแรกที่ `น้ำหนัก ≤ upToG` → ราคาของขั้นนั้น · น้ำหนักเกินขั้นสูงสุด → ปฏิเสธ
**ยอด:** `ค่าธรรมเนียมร้าน + ค่ากล่อง + ค่าส่ง` → ลูกค้าเห็นเป็น "ค่าส่ง" บรรทัดเดียว

**รูปข้อมูลการตั้งค่า (`db.shop.parcel`):**
```
{ fee: 0,
  boxes: [{ name, dims:{w,l,h}, volumeCm3, boxG, price }],
  rates: { [boxName]: [{ upToG, price }] } }
```
ตรวจตอนบันทึก: ชื่อกล่องไม่ซ้ำ · ขั้นน้ำหนักเรียงขึ้นและไม่ติดลบ · ทุกกล่องมีขั้นครบ (ไม่มีช่องว่าง) · ราคาไม่ติดลบ

**Snapshot:** ออเดอร์เก็บ `{box, boxPrice, shipping, fee, weightG}` ตอนสั่ง ตารางที่แก้ทีหลังไม่กระทบออเดอร์เดิม

## 6. การตัดสินใจที่ผมเลือกเอง (แก้ได้)
- ค่ากล่องบวกแยกจากตาราง (ตารางคิดเฉพาะค่าขนส่ง)
- น้ำหนักในตารางรวมกล่อง
- ตัดน้ำหนักปริมาตร (volumetric) ออก เพราะกล่องถูกเลือกจากปริมาตรแล้ว
- ค่าธรรมเนียมร้านเป็น 0 ได้
- ปฏิเสธออเดอร์แทนการเดาราคา เมื่อเกินกล่องใหญ่สุดหรือน้ำหนักเกินตาราง

## 7. สิ่งที่เหลือให้ผู้สร้างตัดสิน
- รูปแบบ UI ของตารางในหน้าตั้งค่า (ใช้แบบ `payment.accounts` เดิม)
- ชื่อฟังก์ชันและโครงไฟล์ตามแผนที่อนุมัติ

## 8. การตรวจสอบ
- Unit: เลือกกล่องเล็กสุดที่ใส่ได้ · ขอบปริมาตรพอดี · เกินกล่องใหญ่สุด → error · น้ำหนักเกินขั้น → error · สินค้าไม่มีน้ำหนัก/ขนาด → error · ค่าธรรมเนียม 0 · ตรวจการตั้งค่า (ลำดับ/ติดลบ/ช่องว่าง)
- Deno: ค่าส่งที่ server คิดตรงกับ `parcelFee` · ค่าส่งที่ client ส่งมาไม่มีผล
- e2e: ตั้งค่าแล้วบันทึก · ลูกค้าเห็นบรรทัด "ค่าส่ง" อย่างเดียว
- `npm test`, `npm run test:fn`, `npm run build`, `npm run test:bundle`
